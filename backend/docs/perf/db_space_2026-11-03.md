# DB 공간 효율 실측 — 운영 1년 규모(2026-11-03)

> 결론: 같은 데이터가 **1,182MB → 807MB(−32%)**. 다시 만든(VACUUM FULL) 예전 구조와 견줘도 **−26%**라 재구축 효과가 아니라 설계 효과다.
> 기사 주소 인덱스는 **291MB → 30MB**, 같은 쿼리는 같은 실행 계획에 더 적은 버퍼로 돌았다(전 종목 정렬 144 → 70ms).
> 1년 치 타입 정리 마이그레이션은 **61~70초**가 걸렸다(두 번 실행 — 서비스 중단 추정치, `vm.sh update` 는 서비스를 멈춘 채 실행).
> 수명주기(13개월 보관)를 켜면 3년 뒤 뉴스·검색 DB 는 약 2.77GB 가 아니라 **약 0.69GB**에서 멈춘다.
> 설계·결정: [ADR-0027](../adr/0027-db-storage-and-lifecycle.md) · 표준: [docs/db/standards.md](../db/standards.md)

## 1. 방법
- 도구: `tools/db_lab.py` — `seed`(합성 데이터) · `measure`(표·인덱스·TOAST 크기, 행 수) · `bench`(대표 쿼리 31회 중앙값) · `compare`.
  DB 이름에 `lab`·`test` 가 없으면 아무것도 하지 않는다.
- 데이터(1년 규모): 뉴스 100만(구글 뉴스 RSS 처럼 180자 주소·한글 제목, 10% 는 발행 시각 없음) · 종목 태깅 130만 · 감성 100만 ·
  검색 36.5만 · 접속 36.5만 · 지갑 원장 20만 · 출석 15만 · 일봉(OHLC·종가 요약) 150종목 × 3년 · 해외 일봉 50종목 × 3년 ·
  채팅 10만 · 학습 10만 · 경보 5만 …(사용자 2,000명). 형식이 깨진 값 5개를 일부러 넣었다(빈 문자열·`N/A`·2월 30일·13월·`2026/10/31`).
- 순서: 예전 코드로 스키마 생성 → 시드 → 예전 코드 `init_db` 한 번 더(예전 앱이 하던 정리까지) → `VACUUM ANALYZE` → 측정(**정리 전**)
  → 복사본에 `VACUUM FULL`(**정리 전·재구축** — 재구축 효과를 떼어 내려고) → 새 코드 `init_db`(시간 측정) → `VACUUM ANALYZE` → 측정(**정리 후**).
- 환경: PostgreSQL 16.15(Ubuntu 24.04) · 이 작업 환경의 컨테이너(학교 VM 은 더 느릴 수 있다 — 시간은 상대 비교로).

## 6. 마이그레이션 — 1년 규모에서 61~70초
| 표 | 행 | 초 | 깨진 값 |
|---|---:|---:|---|
| news | 1,000,000 | 22.6 | 발행 시각 3(빈 문자열·N/A·2월 30일) → NULL + 격리소에 원값 |
| news_sentiment | 1,000,000 | 9.8 | |
| access_log | 365,000 | 5.5 | 1(13월) → NULL |
| search_log | 365,000 | 4.6 | |
| 나머지 36개 표 | | 15.6 | 출석 1(`2026/10/31` — 유일 제약 열이라 NULL, 행은 유지) |
| **합계**(표 정리 58.1초 + 인덱스·권한·원장 보강 = `init_db` 61.3초) | | **58.1** | |
- 40개 표·72개 열. 표마다 ① 깨진 값 세기 ② 격리소(`data_quality_issue`)에 기본키·원값 ③ ALTER 한 번(표를 한 번만 다시 쓴다)
  ④ 바뀐 뒤 '값 있는 행 = 전 − 깨진 값' 대사 — 다르면 전체 롤백 ⑤ ANALYZE. 요약은 `app_meta 'migration:retype:<시각>'`.
- 다시 돌리면 할 일 없음(멱등). 학교 VM 이 이 환경보다 2~3배 느리면 2~4분 — `vm.sh update` 는 서비스를 멈춘 채 실행한다.

## 7. 수명주기(압축 보관 → DB 정리)
실험 DB 복사본에 보관 일수 300일을 줘서 두 달(2025-11·12)을 보관했다.
| 데이터셋·달 | 행(표 셋 합) | 원본 JSON Lines | gzip | 압축 |
|---|---:|---:|---:|---:|
| 뉴스 2025-11 | 253,151 | 42.5 MB | 8.1 MB | 5.2배 |
| 뉴스 2025-12 | 280,272 | 47.3 MB | 9.0 MB | 5.2배 |
| 검색 2025-11 | 27,999 | 3.3 MB | 0.2 MB | 14.7배 |
| 검색 2025-12 | 31,000 | 3.7 MB | 0.2 MB | 14.8배 |
- 59만 행을 17.6초에 보관·검증·정리, 재해시 4개 0.06초. 정리 뒤 `VACUUM` 으로 재사용 가능한 빈자리 73MB
  (뉴스 50.4 · 감성 10.5 · 태깅 9.0 · 검색 3.5 — pgstattuple). 새 행이 그 자리를 채우므로 표가 더 커지지 않는다.
- 3년 추정(뉴스·검색 4개 표): 예전 구조·정리 없음 923MB × 3 ≈ **2.77GB** → 타입 정리 + 13개월 보관이면 591MB ÷ 12 × 14 ≈ **0.69GB**에서
  멈추고, 보관 파일이 한 달 약 8.7MB씩(서버 디스크·외부 보관) 쌓인다. 매일 백업(pg_dump)도 그만큼 작아진다.

## 8. 백업 압축(pg_dump 16, 정리 후 DB)
| 방식 | 크기 | 시간 |
|---|---:|---:|
| gzip 6(예전 기본) | 124 MB | 35.6초 |
| **zstd 3(새 기본 — pg_dump 16+·zstd 지원 시)** | **111 MB** | **4.6초** |
| lz4 | 211 MB | 3.3초 |
| zstd 9 | 107 MB | 17.3초 |
- zstd:3 이 gzip:6 보다 **7.7배 빠르고 10% 작다** — 백업이 서버를 붙잡는 시간이 30초 넘게 준다. `BACKUP_COMPRESSION` 으로 고정 가능.
  (덤프는 날짜도 글자로 쓰므로 타입 정리만으로는 덤프 크기가 거의 같다 — 줄이는 건 수명주기다.)

## 9. 재현
```bash
python tools/db_lab.py seed --db postgresql://oos:oos@127.0.0.1:5432/outofstock_lab      # 예전 스키마 DB 에
python tools/db_lab.py measure --db … --label "정리 전" --out var/db_lab/before.json
DATABASE_URL=postgresql+psycopg://…/outofstock_lab python -c "from app import db; db.init_db()"   # 타입 정리(시간 측정)
python tools/db_lab.py measure --db … --label "정리 후" --out var/db_lab/after.json
python tools/db_lab.py compare var/db_lab/before.json var/db_lab/after.json
```
