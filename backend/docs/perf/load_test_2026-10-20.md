# 부하 시험 · 병목 개선 보고서 — 2026-10-20

제로트러스트(세션 검증·PDP·RLS·감사)를 붙인 뒤에도 화면 사용 패턴에서 오류 없이 버티는지, 어디가 병목인지 재고 고친 기록이다.
숫자는 개발 컨테이너(2 vCPU · 8GB, 부하 발생기와 서버가 같은 기계) 기준이라 **절대값보다 같은 조건에서의 전후 비율**을 본다.

## 1. 시험 방법

| 항목 | 내용 |
|---|---|
| 도구 | `tools/loadtest.py` — 가상 사용자 스레드, 사용자마다 한 번 로그인한 세션(기기 결속 유지)으로 반복 |
| 시나리오 | 비로그인 열람 60% (지수·추천·뉴스·종목·사전·해외·검색) · 로그인 화면 35% (내 정보·지갑·배지·관심·채팅·투자) · 쓰기 5% (검색 기록) |
| 규모 | 동시 사용자 20명 × 30초 (워밍업 제외 실측 약 25초) |
| 서버 | uvicorn 1 worker(개선 비교) / 4 workers + `RATE_LIMIT_BACKEND=postgres`(운영 구성) |
| 병목 찾기 | `pg_stat_statements` 상위 쿼리(`tools/pg_top_queries.py`) → `EXPLAIN (ANALYZE, BUFFERS)` → 고치고 같은 조건으로 재측정 |
| 원자료 | `docs/perf/loadtest/2026-10-20_*.json` · 상위 쿼리 표 `…_top_queries_before.md` / `…_after.md` |

재현:
```bash
python tools/pg_top_queries.py --reset
python tools/loadtest.py --users 20 --seconds 30 --json out.json          # --etag: 브라우저처럼 조건부 요청
python tools/pg_top_queries.py --limit 10 --md top.md
python tools/loadtest.py --compare-polling --users 10 --seconds 20        # 폴링 vs SSE 요청 수
```

## 2. 결과 요약

| 단계(1 worker) | 처리량 | 오류 | 로그인 화면 p50 / p95 | 비로그인 p50 / p95 | 비고 |
|---|---:|---:|---|---|---|
| ① 기준(제로트러스트 적용 직후) | 110.3 RPS | 0 | 147 / 455 ms | 169 / 320 ms | `/me` p50 397ms 가 가장 느림 |
| ② + RLS 세션 변수 캐시 · LIFO 풀 | 116.0 RPS | 0 | 169 / 403 ms | 155 / 278 ms | `/me` 397 → 326ms, `my_overview` 31.6 → 15.6ms |
| ③ + 해외 종목 쿼리 재작성 | **123.7 RPS** | 0 | 153 / 362 ms | 146 / 264 ms | `/overseas/list` p50 212 → 180ms · p95 331 → 272ms |

| 운영 구성(4 workers, 공유 속도 제한 = PostgreSQL) | 처리량 | 오류 | 로그인 p50 / p95 / p99 | 비로그인 p50 / p95 / p99 |
|---|---:|---:|---|---|
| ②까지 적용 | 183.4 RPS | 0 | 88 / 192 / 263 ms | 104 / 167 / 201 ms |
| ③까지 적용(최종) | **185.4 RPS** | 0 | 91 / 203 / 277 ms | 100 / 168 / 197 ms |

4 workers 에서는 2 vCPU 를 부하 발생기와 나눠 쓰는 CPU 한계에 먼저 닿아, DB 쿼리 개선이 처리량보다 **꼬리 지연**(해외 목록 p95 208 → 179ms)으로 나타난다.

## 3. 병목과 개선

### 3-1. RLS 세션 변수 — 커넥션을 꺼낼 때마다 쓰던 왕복을 '바뀔 때만'

행 수준 보안(V010)은 커넥션마다 `app.rls`·`app.user` 세션 변수로 주체를 알려 준다. 처음 구현은 풀에서 꺼낼 때마다
`set_config` 를 실행해(요청당 2~6회 왕복) 로그인 화면이 느려졌다.
- 커넥션 레코드에 마지막 값을 캐시하고 **값이 다를 때만** 실행(`app/db.py` checkout 훅).
- 풀을 LIFO 로 — 방금 쓴 커넥션(같은 사용자일 가능성이 큰)을 다시 꺼내 캐시 적중률을 높인다.
- 결과: `/me` p50 397 → 326ms, 내 정보 집계(`my_overview`) 단독 31.6 → 15.6ms. 보안 수준은 그대로(값이 다르면 반드시 다시 설정).

### 3-2. 해외 종목 목록 — 총 소요 1위 쿼리 (pg_stat_statements)

개선 전 상위 1위: 종목마다 최근 일봉 2개를 구하려고 **전체 일봉에 `ROW_NUMBER()`** 를 매긴 뒤 2개만 남겼다.

| | 호출 | 총 ms | 평균 ms | 최대 ms |
|---|---:|---:|---:|---:|
| 개선 전 (부하 중) | 64 | 2,598.6 | **40.60** | 177.2 |
| 개선 후 (부하 중) | 128 | 142.9 | **1.12** | 7.9 |

- 재작성: 종목 목록을 PK 인덱스로 건너뛰며 뽑고(**loose index scan**, 재귀 CTE), 종목마다 인덱스를 거꾸로 2행만 읽는다
  (`CROSS JOIN LATERAL … ORDER BY trade_date DESC LIMIT 2`). 읽는 행 수가 '전체 일봉'에서 '종목 수 × 2'로 줄었다.
- 단독 측정(Python 포함 왕복): 11.2 → 3.4ms / 호출, `EXPLAIN ANALYZE` 12.3 → 3.3ms.
- 결과가 같은지: 전 종목·일부 종목(중복·없는 종목 포함)·빈 목록 세 경우를 옛 쿼리와 비교해 동일, `tests/test_overseas*.py` 통과.
- 개선 뒤 상위 쿼리는 모두 평균 2ms 미만(최대 `MAX(trade_date) … ANY`, 평균 1.67ms — 종목 17개에서는 LATERAL 판과 차이 0.3ms 라 그대로 둠.
  실데이터 유니버스(150종목+)에서 다시 재 볼 후보).

### 3-3. 전송량 — 조건부 요청(ETag/304)

공개 조회 응답에 약한 ETag 를 붙이고 `Cache-Control: no-cache`(저장하되 쓸 때마다 확인)로 내보낸다. 개인 응답은 `no-store`.

| 같은 시나리오 | 공개 응답 전송량 | 304 비율 |
|---|---:|---:|
| ETag 없이 | 28,322 KB | — |
| 브라우저처럼 If-None-Match | **3,893 KB (−86%)** | 84% |

용어사전(약 130KB)·뉴스 홈처럼 크고 자주 안 바뀌는 응답에서 효과가 크다. 오래된 시세를 보여 주지 않도록 '확인 없는 재사용'은 하지 않는다.

### 3-4. 실시간 알림 — 폴링 대신 SSE

채팅·지갑·친구 알림을 2초 폴링하던 화면을 서버 전송 이벤트(SSE, PostgreSQL LISTEN/NOTIFY)로 바꿨다.

| 20초 · 사용자 10명 | 요청 수 |
|---|---:|
| 2초 폴링 | 100 |
| SSE | 10 (사용자당 연결 1개 — 최대 30분 유지 후 재연결) |

폴링은 사용자당 분당 30요청, SSE 는 30분에 연결 1개다. 알림은 커밋될 때만 나가므로(롤백된 송금의 잔액 알림 없음) 정합성도 해치지 않는다.

## 4. 복원력 설정(같이 넣은 것)

| 설정 | 값(API) | 효과 |
|---|---|---|
| `DB_STATEMENT_TIMEOUT_MS` | 5,000 | 느린 쿼리 하나가 커넥션 풀을 붙잡지 않게 DB 가 끊는다 |
| `DB_IDLE_TX_TIMEOUT_MS` | 60,000 | 트랜잭션을 연 채 멈춘 연결 정리(잠금 보유 방지) |
| 외부 호출 서킷 브레이커·격벽 | 연속 5회 실패 → 60초 차단, 동시 8개 | 외부 API 장애가 워커를 다 붙잡지 않게(`app/security/egress.py`) |
| 공유 속도 제한 | PostgreSQL(UNLOGGED 표 + advisory lock) | 워커·서버가 여럿이어도 한도가 하나로 |

## 5. 한계와 다음 단계

- 부하 발생기와 서버가 같은 2 vCPU 에서 돌아 4 workers 수치는 CPU 경합의 영향을 받는다. 별도 기기에서 재면 더 높게 나온다.
- 로그인 화면 p95 가 비로그인보다 높은 이유는 세션 검증(DB 조회 1회)·RLS 문맥·감사 대상 동작 때문이다 — 보안 비용으로 감수하고,
  세션 조회는 PK 단건(평균 0.13ms)이라 더 줄일 여지는 작다.
- 다음 후보: `MAX(trade_date) … ANY(:ts)` 를 LATERAL 로(유니버스가 커지면), 용어사전 응답의 압축 사전 생성(정적 파일화).
