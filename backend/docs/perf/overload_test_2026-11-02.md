# 과부하 시험 — 대량접속제어가 핵심 거래를 지키는가(2026-11-02)

금감원 「금융IT 안정성 강화를 위한 가이드라인」(2023.11)의 성능 관리 — 임계치 4단계(정상·주의·경계·심각), 경계·심각 시 성능관리보고서,
'대량접속제어 등 성능관리 비상대책' — 를 서버 안에 넣은 뒤(ADR-0023), **넘쳤을 때 핵심 거래가 살아남는지**를 같은 조건에서 켜고 끄며 쟀다.

## 1. 방법

| 항목 | 내용 |
|---|---|
| 서버 | uvicorn 1 worker · `CAPACITY_MAX_INFLIGHT=24` · `LOG_LEVEL=WARNING` · 같은 DB(개발 DB, 시세·뉴스 적재된 상태) |
| 비교 | `CAPACITY_ADMISSION=off` → `on` 만 바꿔 두 번 |
| 부하 | 공개 조회(low) 60 클라이언트 — 시세 순위·뉴스 홈·지수·해외 목록·추천을 쉬지 않고(503 이면 0.2초 뒤 재시도 — 성급한 클라이언트) |
| | 핵심 거래(critical) 4 클라이언트 — 토큰 갱신(갱신 토큰 회전 + 세션 행 잠금 + 토큰 발급) 반복 |
| 시간 · 장비 | 20초 · 개발 컨테이너 2 vCPU(부하 발생기와 서버가 같은 기계 — 절대값보다 같은 조건의 전후 비율을 본다) |
| 도구 | `python tools/overload_test.py --base http://127.0.0.1:8101 --low 60 --critical 4 --seconds 20 --json out.json` |
| 원자료 | `loadtest/2026-11-02_overload_admission_off.json` · `…_on.json` |

## 2. 결과

| | 대량접속제어 끔 | 대량접속제어 켬 | 변화 |
|---|---:|---:|---|
| 핵심 거래 p50 | 718 ms | **216 ms** | −70% |
| 핵심 거래 p95 | 899 ms | **354 ms** | −61% |
| 핵심 거래 p99 | 986 ms | **428 ms** | −57% |
| 핵심 거래 처리 수(20초) · 성공률 | 66 · 100% | **199 · 100%** | 3배 |
| 공개 조회 처리(200) · 초당 | 1,139 · 60.9/s | 770 · 41.9/s | −31% |
| 공개 조회 즉시 거절(503 + Retry-After) | 0 | 2,047 | 경계·심각에서 low 를 먼저 양보 |
| 공개 조회 p95(처리된 것) | 1,108 ms | 447 ms | 줄이 짧아져 처리된 것도 빨라짐 |

**해석** — 끄면 핵심 거래가 공개 조회와 같은 줄(스레드풀·DB 연결)에 서서 0.7초씩 기다렸다. 켜면 동시 요청이 한도의 80%(경계)를 넘는 순간부터
공개 조회를 DB·스레드를 쓰기 전에 돌려보내, 핵심 거래가 1/3 지연으로 3배 처리됐다. 대가는 공개 조회 일부의 503 — 화면은 '접속이 많아요'를 보여 주고
Retry-After 뒤 다시 받는다. 지연이 0이 되지 않은 것(216ms)은 같은 2 vCPU 에서 부하 발생기·거절 처리도 CPU 를 쓰기 때문.

## 3. 성능관리보고서(자동 기록 — `/admin/capacity`)
켠 시험에서 경계 → 심각으로 올라갈 때마다 1건씩 남았다(같은 단계는 10분에 1번). 예(심각 진입 순간):
`동시 요청 51/24 · DB 연결 4/30 · p95 390ms · 돌려보낸 low 319건` + 느린 경로 5개 + 권고(워커 수·증설 검토 — 가이드라인: 경계·심각은 즉각 증설).
끈 시험에서도 심각 보고서는 남는다(차단 없이 '보고·경보'만).

## 4. 운영 기준(제안)
| 단계 | 기준(워커별 — 셋 중 가장 나쁜 것) | 자동 동작 | 사람이 할 일 |
|---|---|---|---|
| 정상 | 동시 요청·연결 < 60%, p95 < 500ms | — | — |
| 주의 | 60~80% 또는 p95 ≥ 500ms | 지표만 | 추이 관찰, 증설 필요성 검토 |
| 경계 | 80~95% 또는 p95 ≥ 1s 또는 5xx ≥ 5% | 공개 조회(low) 503 · 보고서 · 경보 | 원인 분석(느린 경로·DB) · 증설 추진 |
| 심각 | ≥ 95% 또는 p95 ≥ 3s 또는 5xx ≥ 20% | low·normal 503(핵심 거래만) · 보고서 · 경보(error) | 즉시 증설·트래픽 차단 판단 · 필요하면 기능 비상 차단 |
