## 1. 요약
매일 23:00 배치(`run.py real`)의 KRX 시세 적재가 **마지막 단계에서 예외로 끝나 트랜잭션 전체가 롤백**되었다.
적재 메타데이터(종목별 실데이터 시작일 `krx_since`, JSON)가 `app_meta.value VARCHAR(2000)` 한도를 넘었기 때문이다.
시세가 쌓이지 않아 추천 엔진의 최소 이력(25거래일)을 채운 종목이 0개가 되었고, 홈 '오늘의 추천 종목'이 비었다.

## 2. 영향
- 홈 '오늘의 추천 종목 Top 5' 미표시(적격 0종목). 종목 차트의 국내 일봉은 최근 8거래일만 표시.
- PER·PBR 등 재무 지표 일부 미표시 — 같은 회차의 DART 재무 단계도 실패했다(원인은 별건, 6절 참고).
- 데이터 손실 없음(롤백이므로 잘못된 값이 들어가지 않았다), 개인정보·보안 영향 없음.

## 4. 원인 분석
### 직접 원인
`app_meta.value` 가 `VARCHAR(2000)` 이었다. 적재가 끝날 때 `krx_since`(종목코드→시작일 JSON)를 저장하는데,
종목이 84개를 넘으면 2,000자를 넘는다(156종목이면 3,744자). 그래서 PostgreSQL 이 `value too long for type character varying(2000)` 오류를 냈다.
적재는 한 트랜잭션이라(원자성) 그날 받은 수천 행의 시세까지 함께 롤백되었다.

### 근본 원인(왜 늦게 알았나)
1. **적재 후 검증이 없었다** — "몇 종목·몇 일치가 들어갔어야 하는가"를 확인하지 않아, 0행 적재가 '성공처럼' 지나갔다.
2. **실패를 알리는 경로가 없었다** — 실패는 로그와 실행 이력(pipeline_run)에만 남았다. 사람이 보지 않으면 모른다.
3. **화면이 원인을 말하지 않았다** — "추천할 종목이 없어요"만 보여 사용자가 데이터 문제인지 기준 문제인지 알 수 없었다.
4. **스키마 설계** — 길이를 예측할 수 없는 설정값(JSON)에 길이 제한 컬럼을 썼다. 데모·테스트 데이터(수십 종목)에서는 한도에 닿지 않았다.

## 6. 별건: DART 재무 수집 실패(VM)
같은 회차에 DART 단계도 실패했다. 당시 기록에는 원인 문구가 없어 확정하지 못했다(진단 도구가 오류 요약을 출력하도록 보완함).
가능성: VM 외부망 차단(학교 방화벽·프록시), TLS 가로채기, 키 상태 코드(010·011·012·020·901).
보완: 상태 코드 의미 표시 + 치명 코드는 그 회차 즉시 중단(헛호출 방지), 연결 오류 유형별 조치 문구,
회사 코드 목록 7일 캐시(받기 실패 시 저장본 사용). **VM 에서 진단 도구 재실행 후 이 절을 갱신한다.**

## 8. 배운 점
- "실패하지 않았다"와 "기대한 만큼 들어왔다"는 다르다 — 적재는 **기대치와 비교해 검증**해야 끝난 것이다(BCBS 239 의 완전성·적시성 원칙).
- 장애는 사용자가 아니라 **시스템이 먼저** 알아야 한다. 알림은 중복 억제와 비밀값 가림까지 갖춰야 운영할 수 있다.
- 테스트 데이터 규모(수십 종목)가 운영 규모(150종목+)를 대표하지 못했다 → 경계값(긴 메타값) 테스트를 추가했다.
