# 개인정보 내부 관리계획(견본) — OUTOFSTOCK

> 「개인정보의 안전성 확보조치 기준」 제4조가 요구하는 내부 관리계획을 이 서비스에 맞춰 쓴 **견본**이다(졸업 작품 — 실제
> 운영 조직이 생기면 이름·연락처·승인란을 채워 확정한다). 2025.10.31 시행 개정으로 접속기록 점검 주기·방법·사후조치를
> 이 계획에서 정하도록 바뀌었고(제8조②), 출력·복사(제12조)·파기(제13조) 항목이 추가됐다. 각 절의 '도구' 는 실제로 돌아가는
> 코드·명령이다 — 계획이 문서로만 남지 않게. 기술 근거: [`compliance_mapping.md`](compliance_mapping.md)

## 1. 개인정보 보호 조직 · 2. 보호책임자 지정 · 3. 역할과 책임

## 6. 접근 통제 (제6조)

- 관리 기능: TOTP(일회용 비밀번호) 필수 + nginx 관리 기기 인증서(운영에서 `ADMIN_REQUIRE_CLIENT_CERT=true`).
- 서버 접속: SSH 키 · 관리자 대역만(`ADMIN_CIDR=… bash deploy/vm.sh harden`) · root 원격 로그인 금지.
- 미사용 자동 차단: 세션 유휴 30분 · 관리 권한 30분.
- 공개 범위: API 문서 숨김 · 공개 포트는 경계(nginx) 하나 — `python tools/security_check.py` 로 분기마다 확인.

## 7. 암호화와 키 관리 (제7조)

| 대상 | 방식 |
|---|---|
| 비밀번호 | PBKDF2-SHA256 600,000회 + 솔트 + 페퍼(일방향) |
| 채팅·외부 토큰·결제 키·TOTP 비밀 | AES-256-GCM 봉투 암호화(값마다 DEK, AAD 로 행 결속) |
| 전송 | TLS 1.2/1.3 · (DB 가 다른 서버면) 앱↔DB TLS verify-full |
| 백업 | age 공개키 암호화(수신자 2개: 운영·금고) |

키 수명 주기:
1. **생성** — `python3 -c "import os,base64;print(base64.b64encode(os.urandom(32)).decode())"` (마스터·데이터 키 각각, 서로 다르게 — 점검 KEY-3).
2. **보관** — 서버 `.env`(600) + 오프라인 금고 사본 1부. 백업 복호화 키(age identity)는 **서버에 두지 않는다**(오프라인 2부).
3. **교체** — 연 1회 또는 유출 의심 즉시: 새 키를 `DATA_ENCRYPTION_KEY` 에, 예전 키를 `DATA_ENCRYPTION_KEYS_OLD` 에 → 재시작 →
   `python run.py crypto-rotate`(모든 값 재포장) → 복구 훈련으로 키 링 점검 통과 확인 → 예전 키 제거. 마스터 키도 같은 방식(`APP_SECRET_KEYS_OLD`).
4. **파기** — 교체 완료 확인 뒤 예전 키를 `.env`·금고에서 지우고 파기 기록.

## 9. 악성프로그램 등 방지 (제9조)

- 서버: 보안 업데이트 자동 설치(`vm.sh harden` — unattended-upgrades), 긴급 공지 시 즉시 패치.
- 의존성: 해시 고정 + 주 1회 취약점 점검(CI 예약 실행) · 취약점 공지 시 잠금 파일 갱신 → CI 통과 후 배포.
- 업로드 기능 없음(악성 파일 유입 경로 차단).

## 11. 물리적 안전조치

서버는 클라우드·학교 VM(제공자 책임). 관리 PC 는 화면 잠금·디스크 암호화, 관리 기기 인증서(.p12)는 암호로 보호하고 분실 시 CA 재발급.

## 12. 유출사고 대응

1. **탐지** — 보안 이벤트 경보·이상 송금(FDS)·관리자 헬스 이상.
2. **차단(피해 확산 방지)** — 해당 세션·사용자 전체 폐기, 계정 잠금, 의심 관리자 자격 회수. 돈이 오가는 기능이 의심되면
   **기능별 비상 차단**(`POST /admin/controls/{transfer|charge|shop|invest}/pause` — 보안·운영 관리자 한 사람이 즉시, 사유 필수).
   원장 변조·마감 실패·FDS 차단 급증은 시스템이 자동으로 멈춘다(ADR-0023). 키 유출 의심이면 §7 교체.
   세션 탈취 의심(다른 기기 키·키 없는 갱신)은 자동으로 그 사용자 전 세션 종료(ADR-0024).
3. **조사** — 요청 ID 로 접근 로그·보안 이벤트·감사 기록을 잇는다. 감사 체인·외부 증인으로 기록 변조 여부 확인.
4. **통지·신고** — 개인정보 보호법 제34조에 따라 유출을 알게 된 때부터 72시간 안에 정보주체 통지, 신고 대상(규모·정보 종류·
   외부 불법 접근 여부 — 시행령 기준 확인)이면 개인정보보호위원회·KISA 신고. 결정은 보호책임자.
5. **복구·재발 방지** — 필요 시 백업 복원(`vm.sh restore`, 검증 통과 후 전환) → 원인을 확인한 사람이 **재개 요청**(사유 = 확인 결과)
   → **다른 관리자가 승인**해야 기능이 다시 열린다(2인 통제 — 원인 확인 없는 재개가 2차 사고의 흔한 경로) → 사고 보고서(`docs/incidents/` 양식)
   → 계획·위협 모델 갱신. 부하로 인한 장애는 성능관리보고서(`/admin/capacity`)를 첨부한다.

**장애·사고 보고(전자금융감독규정 시행세칙 제7조의4를 설계 기준으로 — ADR-0026)**
- **인지** — 1분 합성 모니터링이 10분 이어진 실패·지연을 장애 사건으로 자동 등록·경보한다. 보안 침해·데이터 오류·감시 공백 동안의
  장애는 당번이 `POST /admin/incidents`(보안·운영 관리자)로 등록한다 — 보안 침해는 등록 즉시 보고 대상.
- **판정** — 지연·중단 30분 이상(또는 10분 이상 + 가입자 1만 명 이상)이면 보고 대상, 최초 보고 기한 = 인지 + 24시간(6시간 전·초과 알림).
  중대 IT 장애는 5개 지표 중 2개 이상(자체 기준 — `GET /admin/incidents` 의 `criteria`).
- **보고서** — `GET /admin/incidents/{번호}?fmt=md`(또는 `run.py incident-report`)로 별지 제2호 항목 순서의 초안을 받아, 원인·처리결과·대책을
  채우고(`POST /admin/incidents/{번호}`) 보고 단계(최초·중간·종결)를 기록한다. 사고원인 칸의 '변경시점 후보'(사건 전 24시간 배포)를 먼저 확인한다.
- **경보 확인** — 오류 경보는 받은 사람이 `POST /admin/alerts/{번호}/ack` 로 확인한다. 15분 안에 아무도 확인하지 않으면 한 번 더 보낸다(상향).
  확인까지 걸린 시간(MTTA)과 미확인 수는 `GET /admin/alerts`·수준진단 점검(`alerts_acked`)이 본다.

## 12-1. 변경관리(프로그램 통제 — 금감원 IT 내부통제, ADR-0026)

1. **요청** — 배포할 설치본으로 `python run.py change-request <설치본> --by 아이디 --title … --reason … --evidence '시험·부하 결과'`.
   설치본을 풀어 사전 영향 분석(돈·인증·스키마·화면·배포 영역, 성능 민감 경로)과 자동 점검(구문·적용된 마이그레이션·정책 형식)을 기록한다.
2. **승인** — **요청자가 아닌** 관리자가 `POST /admin/changes/{번호}/approve`(운영·보안 관리자). 돈·인증·스키마·성능 민감 변경은 검증 근거 없이는
   승인할 수 없다 — 근거 없이 올린 요청은 반려하고 근거를 붙여 다시 요청한다. 승인은 7일 유효, 승인된 설치본 해시와 같아야 배포된다.
3. **배포** — `bash deploy/vm.sh update <설치본>` 이 서비스를 멈추기 전에 지금 배포된 코드로 확인한다(`run.py change-gate`). 평일 08:30~16:00 은
   배포 금지(`CHANGE_FREEZE`). 막혔는데 급하면 `CHANGE_REASON='무엇이 왜 급한지'`(10자↑) — **3일 안에 다른 관리자가 사후 검토**
   (`POST /admin/changes/{번호}/review`, 기한 지나면 매일 알림).
4. **기록** — 적용·실패·되돌림이 무결성 기준선 번호와 함께 남고(감사 체인), 앱 계정은 변경 기록을 지우거나 설치본 해시를 바꿀 수 없다(V017).
- 모드: 금융 운영 `CHANGE_GATE=enforce` · 학교 VM 기본 `record`(막지 않고 '미승인 배포'로 기록 — 수준진단 점검 `change_control` 이 드러낸다).
  어느 모드든 **배포를 깨뜨리는 점검 실패는 막는다**.

## 13. 위험 분석 및 관리

위협 모델(STRIDE)로 위험을 식별하고(`threat_model.md` §3), 위협마다 가능성×영향(고유·잔여)·처리(감소·수용·전가·회피)·담당·
재검토일을 위험 등록부에 둔다(`app/security/risk_register.json` → [`risk_register.md`](risk_register.md), 2026-11). 위험 성향(수용 기준)은
잔여 9 — 넘으면 계획+기한 또는 보호책임자 승인 수용이 있어야 한다(시험이 강제). 재검토는 180일마다(운영 점검 `risk_register` 가 기한 초과를 잡는다).
자산은 코드에서 목록·중요도(C·I·A)를 만든다(`app/security/assets.py`).

**인사조치(퇴직·전보·장기 휴직)** — 보안 관리자가 `POST /admin/users/{아이디}/offboard`(사유 필수) 한 번으로 관리 자격·활성 권한·대기 요청·
세션을 회수하고 계정을 중지한다(전자금융감독규정 제13조 ①11호). 60일 동안 한 번도 켜지 않은 관리 자격은 매일 자동 회수된다
(`ROLE_DORMANT_DAYS` — 다시 필요하면 2인 승인). 부트스트랩(`ADMIN_USERS`) 계정은 설정에서도 뺀다.

## 14. 수탁자 관리

외부 연동 전체(데이터 원천·결제·알림·소프트웨어 공급망)의 중요도·끊김 영향·대체 경로는 [`third_party_register.md`](third_party_register.md).

| 수탁(외부 처리) | 넘기는 정보 | 관리 |
|---|---|---|
| 토스페이먼츠(결제 승인) | 주문 번호·금액(카드정보는 토스가 직접 받음) | 서버 승인 API 로만 · 비밀 키 암호화 보관 |
| 알림 채널(텔레그램·메일, 선택) | 운영 경보 문구(개인정보 넣지 않음) | 웹훅·토큰 비밀 관리 |
| 원격 백업 저장소(선택) | 암호화된 백업만(복호화 키 없음) | 접근 권한·보관 기간 연 1회 확인 |

## 15. 계획의 수립·변경·승인

보호책임자 승인으로 확정한다. 변경은 저장소 이력(이 파일)으로 남기고, 연 1회 이상 검토한다(법령 개정·서비스 변경 시 즉시).

## 16. 그 밖 — 출력·복사(제12조) · 파기(제13조) · 가명정보

- **출력·복사**: 관리자 열람은 목적 필수 + 기록. 분석용 반출은 가명 내보내기만(`python run.py export-pseudonymized` — 목적 필수, 아이디는 내보낼
  때마다 새 솔트 HMAC, 가입일·잔액 등은 구간화). 화면 출력 항목은 업무에 필요한 것만.
- **파기**: 보관 기간이 지나면 매일 배치가 지운다(`privacy.retention_purge` — 지운 건수를 감사 로그에 기록). 탈퇴 시 계정 데이터 즉시
  삭제 + 보안 기록 아이디는 가명으로(보관 기간 동안 추적성 유지). 기능을 없애면 그 기능의 표도 지운다(V009). 백업 안의 사본은
  보관 주기(최근 14개 + 월별 12개) 만료로 소멸.

## 17. 보안 수준 자가진단·보고(금융보안 수준진단 프레임워크)

- **무엇을** — 금융보안원 「금융보안 수준진단 프레임워크」 7개 분야 45개 항목을 이 서비스에 맞춘 카탈로그(`app/security/ssf_catalog.json`)로,
  근거(문서·코드·시험·운영 점검·자동 대응·실측 기록)를 기계가 확인해 성숙도(초기·기반·발전·고도화)를 판정한다(ADR-0025).
- **언제** — 매월 1일 자동(스케줄러) + 큰 변경·사고 뒤 수시(`POST /admin/assessment/run`, 감사·보안 역할). 92일 넘게 진단이 없으면 '기한 초과'.
- **보고** — 분기마다 한 장 요약(분야별 현재·목표·개선 전, 오른 항목, 남은 갭, 범위 상한)을 보호책임자(팀장)·지도교수에게 보고한다
  ([`self_assessment.md`](self_assessment.md) §1 — `python run.py assurance-docs`). 등급이 내려간 항목·실패한 운영 점검은 그때그때 경보.
- **증빙** — 결과는 추가만 저장되고(앱 계정은 수정·삭제 권한 없음) 다이제스트가 감사 체인에 남는다. 지난 결과를 다시 대조할 수 있다
  (`GET /admin/assessment/{id}` 의 `intact`). 감사 수검 때는 이 이력과 근거 목록을 그대로 제출한다.
- **훈련** — 사고 대응 모의훈련(`python run.py incident-drill --target-db …_drill` — 7개 시나리오: 원장 변조·이상 송금 급증·대입 공격·
  쿠키 탈취·파일 변조·서비스 장애 판정·보고·깨진 배포)을 분기 1회, 복구 훈련(§11·DR)과 함께 돌리고 보고서를 `docs/incidents/drills/` 에 남긴다.
- **운영 점검 20종** — 2026-11 2차에 가용성(`uptime_slo`)·보고 기한(`incident_reports`)·경보 확인(`alerts_acked`)·변경 통제(`change_control`)·
  취약점 자가 점검 주기(`pentest_recent`)를 더했다. 실패한 점검은 그 항목의 등급을 '기반'으로 내린다.
