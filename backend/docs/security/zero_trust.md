# 제로트러스트 설계와 자가 진단 — OUTOFSTOCK

> **전제** — 이 서비스는 전자금융업자가 아니다. 아래 기준(KISA 제로트러스트 가이드라인 2.0, 금융보안원 금융분야 제로트러스트
> 보안 안내서, 국정원 N²SF)은 '준수 대상'이 아니라 **설계 기준**으로 썼다. 성숙도·이행 판정은 **자가 평가**이고, 판정마다
> 코드·시험·실측 증거를 붙였다(증거 없는 '이행'은 적지 않는다).
> 관련 문서: 위협 모델 [`threat_model.md`](threat_model.md) · 규정 대응 [`compliance_mapping.md`](compliance_mapping.md) ·
> 개발보안 69개 [`secure_coding_69.md`](secure_coding_69.md) · 검증 보고서 [`verification_report_2026-10-21.md`](verification_report_2026-10-21.md)

## 1. 원칙을 코드로 옮긴 방식

| 원칙 | 이 서비스에서 |
|---|---|
| 암묵적 신뢰 없음 | 내부망·같은 서버라도 믿지 않는다 — 앱↔DB TLS(선택)·DB 계정 분리·RLS, 컨테이너·서비스마다 권한 없음 |
| 매 요청 검증 | 모든 API 경로가 정책 집행 지점(PEP)을 지난다. 세션은 요청마다 다시 확인(만료·유휴·폐기·기기·계정 상태) |
| 최소 권한 | 정책 파일 기본 거부 · 관리 권한은 '자격 + 30분 활성(JIT)' · DB 앱 계정은 DDL 없음 · 서비스는 capability 0 |
| 침해 가정 | 앱이 뚫려도: 홈 폴더 안 보임(systemd) · 바깥으로 못 나감(egress 3중) · 감사 기록 못 고침(해시 체인 + 외부 증인) |
| 가시성 | 요청 ID 하나로 접근 로그·보안 이벤트·감사 기록·DB 알림이 이어진다. 규칙에 걸리면 자동 대응 |

### 요청 한 건의 경로

```
브라우저 ──TLS 1.2/1.3──▶ nginx(경계 PEP: 요청률·본문 상한·/admin 기기 인증서·문서 숨김·전달 헤더 덮어쓰기)
   │  HttpOnly 쿠키(10분 접근 토큰) + CSRF 헤더                         │ 127.0.0.1 / 내부망(web)
   ▼                                                                    ▼
ContextMiddleware(요청 ID·IP 대역·기기 지문) → PEP(세션 확인 → PDP 판정 → CSRF/Origin → 위험 신호)
   → 라우트(입력 검증) → 서비스 → DB 연결 꺼낼 때 RLS 문맥(app.user) 설정 → PostgreSQL(FORCE RLS·최소 권한 계정)
   → 거부·이상 징후는 security_event → 규칙 평가 → 자동 대응(세션 폐기·계정 잠금·IP 차단·알림)
나가는 연결: 앱 허용 목록 검사 → egress 프록시(squid, 같은 목록 + 내부 주소 거부) → (VM) 커널이 직접 연결 차단
```

정책 결정(PDP)은 [`app/security/policy.json`](../../app/security/policy.json) — 동작 29개, 버전 `2026-11-09.1`, 파일 SHA-256 을
판정마다 기록. 정책에 없는 동작은 거부(`unknown_action`), 정책 파일 형식이 틀리면 서버가 뜨지 않는다(안전 실패).
`tests/test_zero_trust.py::test_every_api_route_declares_a_known_policy_action` 이 '모든 경로가 동작 이름을 선언했는가'를,
`test_route_without_policy_is_denied_by_default` 가 '선언 없는 경로는 거부되는가'를 확인한다(경로 146개 — 기각 기능 제거 전 175개).
같은 정책 파일이 동작마다 **중요도**(`tier` — 혼잡할 때 먼저 양보할 순서, ADR-0023), **비상 차단 대상 기능**(`control`),
**기기 결속 증명 필요 여부**(`bind:"device"` — ADR-0024)도 정한다. 접근·혼잡·사고 대응이 한 정책에서 나온다.

## 2. KISA 제로트러스트 가이드라인 2.0 — 핵심 요소별 성숙도(자가 평가)

성숙도 4단계(기존 → 초기 → 향상 → 최적화)의 판정 기준: **기존** 정적·경계 중심·수동 / **초기** 일부 자동화, 요소 간 통합 제한 /
**향상** 중앙 정책·자동 집행·조직 전반 실시간 가시성 / **최적화** 동적 정책 자동 생성·전 자산 실시간 관리·예측 분석.

| 핵심 요소 | 구현(증거) | 판정 | 다음 단계로 가려면 |
|---|---|---|---|
| **식별자·신원** | 요청마다 세션 재확인(`security/sessions.py`) · 접근 토큰 10분 + 갱신 토큰 회전·재사용 탐지(재사용 → 사용자 전체 세션 폐기) · **세션을 기기 키에 결속(DPoP — 키 없는 갱신·다른 키 = 탈취로 종료)** · 비밀번호 정책 + PBKDF2-SHA256 600,000회 + 페퍼 · TOTP 2단계(관리 역할 활성 필수) · 연속 실패 5회 잠금(지수 연장) · 고위험 동작 추가 인증 5분 · 동시 세션 5개 | **향상** | 일반 사용자 2단계 기본화, FIDO2/패스키, 행동 기반 위험 점수로 세션 강도 자동 조정 |
| **기기·엔드포인트** | **브라우저 안의 비추출 ECDSA 키로 세션 결속**(2026-11 — 갱신·돈·계정·관리 동작마다 그 키의 1회용 서명, 쿠키를 복사한 다른 기기는 실패) · 기기 지문(브라우저·OS 계열) 결속 · IP 대역 변경은 위험 신호(FDS) · 관리 경로는 사설 CA 기기 인증서(mTLS) | **초기 → 향상(세션 결속)** | 단말 보안 상태(패치·백신) 확인(MDM/EDR 연동), 기기 등록부·인증서 폐기 목록(CRL) 운영 |
| **네트워크** | compose: 망 4개(outside·web·data·egress, 뒤 셋 internal) — 공개 포트는 edge 하나 · VM: 앱 127.0.0.1 + nginx · TLS 1.2/1.3(ECDHE+AEAD)·HSTS · 앱↔DB TLS verify-full(선택, 평문 TCP 거부 hba) · egress 허용 목록 3중 + DNS rebinding 거부 · 방화벽 기본 거부(`vm.sh harden`) | **향상** | 서비스 간 mTLS(앱↔nginx), 소프트웨어 정의 경계(SDP)·동적 마이크로 세그멘테이션 |
| **시스템** | 컨테이너: 루트 아님·루트 FS 읽기 전용·capability 전부 제거·권한 상승 금지·자원 상한 · systemd 샌드박스 노출 점수 9.0 → 1.2(`systemd-analyze security`) · 해시 고정 의존성·pip 없는 실행 이미지 · SSH·커널·자동 보안 업데이트(`harden`) | **향상** | 이미지 서명·출처 증명(SLSA), 런타임 무결성 감시, 베이스 이미지 다이제스트 고정 |
| **애플리케이션·워크로드** | 모든 경로 PEP + 기본 거부 정책 · CSRF 이중 제출 + Origin · CSP nonce + Trusted Types + 인라인 핸들러 0(`data-on`) · FDS(송금 전 규칙 점수: 허용/추가 인증/차단) · CI: bandit·pip-audit·SBOM·정책 시험(배포 설정 27개) | **향상** | 정책을 위험 점수로 동적 생성, DAST(동적 점검) 정기화, 런타임 애플리케이션 보호 |
| **데이터** | 분류 등록부 L1~L4(모든 표 등록을 시험이 강제) · 개인 데이터 18개 표 FORCE RLS · 봉투 암호화(AES-256-GCM, 값마다 DEK, AAD 로 행 결속, 키 교체) · 감사 해시 체인 + 외부 증인 · 백업 age 암호화 · 보관 기간 파기 · 가명 내보내기 · **자유 입력 DLP(주민번호·카드번호 저장 전 가림 + 로그·알림 출구)** | **향상** | KEK 를 KMS/HSM 으로, 자동 데이터 탐색 |
| 교차: 가시성·분석 | 요청 ID 로 로그·보안 이벤트·감사·접근 기록 연결 · JSON 로그 · 탐지 규칙 9개 · 일일 요약 · 개인정보 열람 점검 리포트 · 관리자 헬스(백업·훈련·이벤트) | **초기~향상** | SIEM 연동·UEBA, 대시보드 상시 관제 |
| 교차: 자동화·통합 | 규칙 → 세션 폐기·사용자 전체 폐기·계정 잠금·IP 차단·알림 자동 · **원장 변조·마감 실패·FDS 급증 → 돈 기능 자동 비상 차단(재개는 2인 승인)** · **부하 단계에 따라 입장 정책 자동 변경(대량접속제어)** · 배포 설정·정책 파일을 CI 가 검사(policy as code) | **향상** | 위협 정보로 정책 자동 갱신(SOAR), 대응 결과 자동 검증 |

## 4. 남은 위험과 정직한 한계

- **RLS 문맥은 앱이 정한다** — `app.rls`·`app.user` 세션 변수는 앱 계정이 바꿀 수 있다. RLS 는 '앱 로직 실수(조건 누락)'를 막는
  2차 방어이지, SQL 주입으로 `SET` 을 실행할 수 있는 공격자를 막지는 못한다. 그래서 1차 방어는 바인딩 파라미터 100%
  (bandit B608 검토)·앱 계정 DDL 없음·감사 해시 체인이다. 근본 해결(행 주인을 DB 역할로)은 계정 수가 사용자 수만큼 늘어 보류.
- **키 보관** — 마스터 키·데이터 키가 `.env`(600)·컨테이너 환경변수에 있다. 서버 침해 시 키도 노출된다. KMS/HSM·비밀 관리자가 다음 단계.
- **단말** — 세션은 브라우저의 비추출 키에 묶였지만(쿠키 복사 방어), 그 PC 를 원격 조종하는 공격자는 같은 브라우저로 요청할 수 있다.
  단말 자체의 신뢰(패치·백신 상태)는 관리 단말(인증서)에만 있다.
- **단일 서버** — DB·앱이 한 호스트(또는 한 compose)라 가용성은 백업·PITR 복구(RTO 실측 수 초~수 분)에 기댄다.
- **자가 평가** — 판정은 외부 감사가 아니다. 판정을 다시 재는 방법은 각 행의 증거(시험·도구)로 남겨 두었다.
