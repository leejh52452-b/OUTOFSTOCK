# ADR-0015 가상머니는 복식부기 원장으로 — 거래마다 합 0, 매일 마감 사슬과 대사

| 항목 | 내용 |
|---|---|
| 상태 | 채택 · 2026-10-20 · **개정 2026-10-24**(정밀 점검 결함 23·24·25·27·32 — 아래 '개정') |
| 범위 | 데이터 처리 — 정합성(BCBS 239 원칙 3) |
| 코드 | `sql/migrations/V012__double_entry_ledger.sql` · `app/services/ledger.py` · `wallet.py` · 스케줄러 00:20 일 마감 · `/admin/ledger` |
| 시험 | `test_ledger.py`(모든 지갑 변동이 균형 분개 · 대사) · `test_wallet_integration.py` · 복구 훈련 '원장 마감 사슬·시산표' 항목 |

## 맥락
지갑은 단식 원장(`wallet_ledger`: 잔액 변동 1줄)이었다. '잔액 = 원장 합'은 확인할 수 있어도, 돈이 **어디서 왔는지**(환영금·충전·송금)를
계정 단위로 맞춰 볼 수 없었다. 버그로 돈이 '생겨도' 단식 원장은 그 사실을 드러내지 않는다.

## 결정
- 잔액이 바뀔 때마다 같은 트랜잭션에서 분개 두 줄: 사용자 계좌 `W<계좌번호>` ± 금액 / 상대 시스템 계정 ∓ 금액.
  상대 계정: 환영금·출석 = `sys:promotion` · 인앱 충전 = `sys:iap_clearing` · 토스 = `sys:pg_clearing` ·
  송금 = `sys:transfer_clearing`(보내는 쪽·받는 쪽이 같은 계정을 거쳐 0 으로 상쇄).
- **지연 제약 트리거** — 커밋 시점에 거래별 합이 0 이 아니면 커밋 자체가 실패(DB 가 보장).
- **일 마감(00:20)** — 전날 계정별 합계를 확정하고 직전 마감의 해시를 이어 붙인다(마감 사슬). 시산표 합 0 · 지갑 잔액 = 원장 합 대사.
  어긋나면 알림 + 관리자 화면에 표시.
- 과거 단식 행(기각 기능의 사유 포함)은 지우지 않는다 — 잔액 재계산의 근거.

## 검토한 대안
| 대안 | 버린 이유 |
|---|---|
| 단식 원장 + 주기 대사 | 계정 간 흐름을 못 본다(판촉비가 얼마나 나갔나, 충전 대기금이 맞나) |
| 앱 코드에서만 합 0 검사 | 다른 경로(수동 SQL·새 코드)로 깨질 수 있다 — DB 제약이 마지막 방어 |
| 이벤트 소싱 전면 도입 | 규모 대비 과함 — 분개 표 + 마감 사슬로 같은 추적성 |

## 결과
- 송금 1건 쓰기가 2행 늘었다(부하 시험 쓰기 비중 5% 에서 영향 측정 불가 수준).
- 복원 검증에 '마감 사슬 재계산·시산표 0'이 들어가 백업이 회계적으로도 온전한지 확인한다.

## 개정(2026-10-24) — 마감이 '빠짐없이·한 줄 한 줄·밖에서도' 맞는지
| 결함 | 문제 | 바꾼 것 |
|---|---|---|
| 24 | 스케줄러는 '어제'만 마감 — 서버가 하루 꺼져 있으면 그날은 영영 마감되지 않고 사슬이 그날을 건너뛰었다. CLI 는 오늘·미래도 마감해 나중에 '변조'로 오경보 | `close_pending()`: 마감 안 한 날을 어제까지 **날짜순으로 차례로**(처음이면 첫 분개일부터). 오늘·미래(자정 5분 여유)·이미 마감한 날보다 앞선 날은 거부. 검증이 **빠진 날(gaps)** 을 따로 보고 |
| 25 | 마감 해시가 합계(건수·차변·대변·계정별 합)만 덮음 — 합계를 유지한 채 거래 사이에서 금액을 옮기는 변조를 못 잡음 | canon 2: 합계 + **분개 한 줄 한 줄의 SHA-256 다이제스트**(DB 안에서 계산). 마감 해시를 **같은 트랜잭션의 감사 로그**(해시 체인 + 외부 증인)에도 기록 → 소유자 권한으로 분개·마감을 함께 다시 계산해 넣어도 감사 체인과 달라 드러남 |
| 27 | 분개마다 앱 시계를 따로 읽음 — 자정에 걸친 송금은 송금 가계정이 이틀로 나뉘어 마감 실패(오경보) | 분개 시각 = DB 트랜잭션 시각(`now()`) — 한 거래는 한 시각 |
| 23 | 탈퇴가 잔액을 잠그지 않고 읽음 · 지갑 생성이 계정 존재를 안 봄 — 진행 중 입금이 '지갑 없는 계좌'에 붕 뜨거나, 탈퇴한 아이디로 지갑이 되살아남 | 지갑 쓰기는 계정 행 `FOR KEY SHARE`(탈퇴 `FOR UPDATE` 와 줄 세움, 잠금 순서 계정 → 업무 행 → 지갑) · 소멸 처리는 `FOR UPDATE` · 마감에 **고아 계좌 0** 대사 추가 |
| 32 | 시작 잔액 분개가 마이그레이션 잠금 밖 — 프로세스 동시 기동 시 두 번 분개 | 트랜잭션 advisory lock |

옛 코드로 각 결함을 재현한 뒤 고쳤다(`docs/security/verification_report_2026-10-21.md` '정밀 점검').
대안으로 '사슬을 마감한 순서로 잇고 빠진 날은 뒤에 붙이기'도 검토했다 — 유연하지만 날짜순 사슬보다 설명·검증이 복잡하고,
catch-up 이 있으면 새 빈 날이 생기지 않는다. 예전 버전이 남긴 빈 날은 고칠 수 없으므로(사슬 중간 삽입 불가) 검증이 정직하게 보고한다.
