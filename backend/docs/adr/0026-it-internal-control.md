## 맥락
2026년 금융당국이 짚은 IT 사고의 원인은 고급 공격보다 **기본 내부통제의 빈틈**이었다 — 배포 전 검증 누락(6.24), 24시간 관제 공백·MFA
미도입(10.14). 이 서비스는 인증·데이터 보호·복원력 통제를 갖췄지만(ADR-0011~0025), (1) 어떤 설치본이든 `vm.sh update` 한 줄로
배포됐고 승인·사전 점검·기록이 없었다, (2) 서비스가 멈춰도 알아채는 것은 사람이었고 '보고 대상인지·언제까지'를 판단할 근거가 없었다,
(3) 경보는 보내기만 하고 누가 봤는지 몰랐다, (4) 공격자 관점의 점검은 단위 시험에 흩어져 있었다.
한국산업은행 고유의 공개 지침은 찾지 못했다 — 산업은행에도 적용되는 전자금융감독규정·시행세칙, 공공기관 암호모듈(KCMVP),
한국은행이 감시하는 지급결제 기준(PFMI)으로 대신했다.

## 결정
1. **변경관리 = 배포 게이트**(`changes.gate`) — `vm.sh update` 가 서비스를 멈추기 **전에**, 지금 배포된(검증된) 코드가 새 설치본을 확인한다.
   - 설치본 SHA-256 을 머리말과 대조해 임시 폴더에 풀고(경로 탈출 거부) **자동 사전 점검**: 파이썬 구문 · 이미 적용된 마이그레이션이
     바뀌지 않았나(바뀌면 기동 때 멈춘다) · 접근 정책 형식 · 수준진단 근거 무결성. 앞의 셋이 실패하면 **어느 모드든** 배포 중단.
   - **사전 영향 분석** — 지금 배포된 파일(무결성 기준선) 대비 바뀐 파일을 돈·인증·스키마·화면·배포 영역으로 묶어 위험도,
     모든 요청이 지나는 경로(성능 민감)를 표시. 돈·인증·스키마·성능 민감 변경은 **검증 근거(시험·부하 결과)** 없이는 승인 불가.
   - **요청자 ≠ 승인자**(제3자 검증) · 승인은 7일 · 승인된 설치본 해시와 같아야 통과(바꿔치기 불가) · **배포 금지 시간**(평일 08:30~16:00).
   - **긴급 변경**(`CHANGE_REASON='사유'`, 10자↑) — 막지 않되 경보 + **3일 안 다른 관리자의 사후 검토**(기한 지나면 매일 알림).
   - 모드: `enforce`(금융 운영) · `record`(기본 — 막지 않고 '미승인 배포'로 기록, 수준진단 점검이 드러낸다) · `off`.
   - 기록(`change_record`)은 앱 계정이 **지우거나 설치본 해시·사유·점검 결과를 고칠 수 없다**(V017 — 상태·승인·적용·검토 칸만).
   - 배포 결과(적용·실패·되돌림)를 무결성 기준선 번호와 함께 남긴다. 되돌리기는 기준선을 다시 기록한다(전엔 되돌린 뒤 모든 파일이
     '변조' 경보) — 이때와 업데이트 때 모두 **설치본·스냅샷 목록에 있는 파일만** 기준선에 넣어, 배포 전부터 있던 낯선 파일은 계속 경보.
2. **장애 자동 판정·사고보고**(`incidents`) — 1분 합성 모니터링(같은 서버의 API 헬스 — 감시 주소는 vm.sh 가 실제 포트로).
   10분 이어지면 장애 사건·경보, **30분이면(또는 10분 + 가입자 1만 명) 보고 대상** — 최초 보고 기한 = 인지 + 24시간(기한 6시간 전·초과 알림),
   정상 3번이면 종료·지속 시간·영향 이용자(그 시간에 살아 있던 세션) 기록. 보안 침해 사건은 등록 즉시 보고 대상.
   보고서 초안은 시행세칙 별지 제2호 12개 항목 순서, '사고원인(변경시점 및 사유 등)'에 **사건 전 24시간의 변경 기록**·심각 보안 이벤트·
   성능관리보고서·비상 차단을 자동으로 붙인다. 중대 IT 장애는 5개 지표 중 2개 이상(지표의 수치는 공개되지 않아 자체 기준).
   안전장치: 한 번도 정상 응답을 받은 적 없는 주소는 장애로 판정하지 않는다(설정 오류 = 가짜 장애 방지) · 확인 기록이 10분 넘게
   비면 '감시 공백' 경고(서버 전체가 꺼진 동안은 같은 서버가 볼 수 없다).
3. **관제**(`alerts`) — 경보 확인(ack: 누가·언제, 같은 사건 묶음) · **15분 동안 아무도 확인하지 않은 오류 경보는 한 번 상향** ·
   MTTA·미확인 지표 · 외부 관제 연동 형식(**CEF·JSON Lines** — 아이디는 로그 줄과 같은 HMAC 가명, 대상 번호는 그대로, 내보내기도 감사 기록).
4. **취약점 자가 점검**(`pentest`) — 침투테스트 가이드라인의 4단계(정보 수집 → 초기 침투 → 권한 상승·내부 확산 → 핵심 자산 접근)로
   22개 비파괴 점검, 항목마다 ATT&CK 기법·KISA 웹 점검 항목 이름. 대상이 이 서비스(루프백·TRUSTED_ORIGINS)가 아니면 승인 근거가
   있어야 시작. 인증 시도 제한은 없는 아이디로 순서대로 몇 번만(동시 요청 없음). 결과는 공격 흐름(어느 단계에서 막혔나)·보고서·
   감사 체인, 183일 넘으면 진단 점검 실패(제37조의2).
5. **훈련에 두 시나리오 추가** — ⑥ 서비스 장애(실패 40분 주입 → 사건·보고 대상·보고서 초안·종료) ⑦ 깨진 배포(구문 오류 설치본 차단 →
   미승인 거부 → 본인 승인 거부 → 다른 관리자 승인 → 적용).
6. **복구 목표** — DR 훈련의 실측 RTO 가 `DR_RTO_TARGET_MIN`(기본 180분 — 제23조)을 넘으면 훈련이 성공해도 진단 점검 실패.

## 검토한 대안
| 대안 | 버린 이유 |
|---|---|
| 깃 브랜치 보호·PR 승인만 | 학교 VM 은 설치본(scp)으로 배포한다 — 실제로 서버에 올라가는 산출물(해시)에 승인을 묶어야 바꿔치기를 막는다 |
| 새 설치본의 코드로 게이트를 돌림 | 새 코드가 게이트를 약하게 바꿀 수 있다 — 지금 배포된(이미 승인된) 코드가 판정 |
| 승인 없으면 무조건 차단(기본 enforce) | 1인 운영 VM 에서 배포가 막히면 장애 복구도 막힌다 — 기본은 기록, 깨진 설치본만 항상 차단, 금융 운영은 enforce |
| 외부 모니터링 SaaS | 외부 전송·계정이 늘고 보고 판정과 이어지지 않는다 — 같은 서버 감시 + 공백 경고, 바깥 감시는 문서로 권장 |
| 경보를 더 자주 반복 | 피로만 는다 — 한 번 상향 + 확인 기록·MTTA 를 진단이 본다 |
| 상용 스캐너(ZAP·Burp)만 | 결과가 이 서비스의 정책·감사와 이어지지 않는다 — 자체 점검은 회귀 시험이 되고, 사람의 침투 시험은 범위 밖으로 명시 |

## 한계
- 같은 서버 안의 합성 감시 — 서버 전체 정지는 공백 경고로만 안다(바깥 감시 필요). 영향 이용자는 세션 기준 추정치다.
- 중대 IT 장애 5개 지표·보고 기준은 설계 기준으로 옮긴 것 — 이 서비스는 보고 의무 대상이 아니고, 지표 수치는 자체 기준이다.
- 게이트는 구문·마이그레이션·정책 형식만 자동으로 본다 — 업무 논리 오류는 시험과 승인 검토가 막는다.
- 자가 점검은 사람의 침투 시험을 대신하지 못한다(업무 논리·사회공학·내부망은 범위 밖). 암호모듈은 AES-256-GCM(OpenSSL) —
  KCMVP 검증필 모듈이 아니다(공공기관 배포 시 ARIA 등 검증필 모듈로 바꿔야 하며, 봉투 암호화의 알고리즘 필드로 교체할 자리를 두었다).
