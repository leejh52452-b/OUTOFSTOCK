# ADR-0002 분석 계층(analytics 스키마)을 서빙 계층과 분리하고, SQL 마이그레이션으로 관리한다

| 항목 | 내용 |
|---|---|
| 상태 | 채택 · 2026-10-10 |
| 범위 | 2번 데이터 플랫폼(전 종목 × 10년), 토스·네이버 기능의 데이터 원천 |
| 코드 | `sql/migrations/V001~V006` · `app/migrations.py` · `app/collectors/krx_history.py` · `app/services/platform.py` · `run.py platform-*` |

## 맥락
기존 화면용 표(`public.ohlc` 등)는 시가총액 상위 150종목(유니버스)만 담아 화면을 빠르게 그리는 **서빙 계층**이다.
'지금 뜨는 산업'·'주식 골라보기'·투자자별 수급·신용위험 모형은 **전 종목(약 2,700) × 10년(약 670만 행)** 이 필요하다.
같은 표에 섞으면 ① 화면 쿼리가 대용량 표를 건드리고 ② 백필(수천 번 호출·수백만 행)이 서비스 잠금과 다툰다.
또 분석 계층은 파티션 표·함수·머티리얼라이즈드 뷰처럼 ORM 메타데이터로 표현하기 어려운 DDL 이 중심이다.

## 결정
1. **스키마 분리**: `analytics` 스키마 = 분석 계층. 화면은 기존 `public` 표, 분석 API·모형은 `analytics` 를 읽는다.
   상장폐지 종목도 지우지 않는다(`security_master.first_seen/last_seen`) — 생존 편향 방지.
2. **SQL 마이그레이션(Flyway 방식)**: `sql/migrations/V001__이름.sql` 을 번호 순서로 한 번씩 적용하고
   `schema_migrations` 에 버전·체크섬(SHA-256)·실행 시간을 남긴다.
   - 이미 적용한 파일의 내용이 바뀌면 **시작을 멈춘다**(운영 DB 와 코드의 스키마가 갈라지는 것을 막음). 변경은 항상 새 파일.
   - `init_db` 의 advisory lock 안에서 돌아 API·스케줄러가 동시에 켜져도 한 번만 적용된다.
   - DDL 은 소유자 계정(`MIGRATION_DATABASE_URL`)으로만 — ADR-0005.
3. **적재 단위 = (거래일, 시장)** 이고 재개 가능하다: 단위마다 `analytics.load_log` 에 ok·empty·failed·행 수·
   원천 체크섬을 남기고 다음 실행은 끝나지 않은 단위만 받는다. 호출 예산을 넘기면 멈추고 다음 실행에서 이어서 —
   매일 배치는 `ANALYTICS_BACKFILL_BUDGET`(기본 1,200번, KRX 하루 한도 10,000번 안), 수동 `platform-load` 는 `--budget`(기본 5,000).
   10년 백필(약 4,900번 호출)을 하루~며칠에 나눠 끝낸다.
4. **대량 적재 = COPY + 병합**: 하루치(약 2,700행)를 COPY 로 임시 표에 넣고 `INSERT … ON CONFLICT` 로 합친다.
   같은 날을 다시 받아도 결과가 같다(멱등), 바뀐 행만 갱신(`IS DISTINCT FROM`), 한 단위 = 한 트랜잭션.
5. **데이터 원천 원칙**: 공식 API 만 쓴다 — KRX OpenAPI(시세), 한국투자증권 Open API(수급·증시자금·투자의견·종목 상태),
   DART(공시·재무), 한국은행 ECOS(금리), 업비트 공개 API(가상자산). 포털 화면을 긁지 않고,
   **증권사 리포트 원문은 저작권 때문에 싣지 않는다** — 대신 1차 자료(공시)와 의견·목표가 숫자만.
   키·네트워크가 없을 때 쓰는 표본은 `source='gen'` 으로 저장해 화면에 '표본'으로 표시하고,
   투자 유의(관리·경고) 표본은 실제 회사가 아닌 가상의 회사만 쓴다.

## 검토한 대안
| 대안 | 버린 이유 |
|---|---|
| 기존 표에 전 종목을 그냥 추가 | 화면 쿼리·적재 잠금이 섞이고, 유니버스 기준(시총 상위)과 분석 기준(전 종목)이 충돌 |
| 별도 분석 DB(ClickHouse 등) | 운영 대상이 하나 늘어난다. 670만 행은 PostgreSQL 파티션·인덱스로 충분(ADR-0003 실측) |
| Alembic | 파티션·함수·MV 는 결국 원시 SQL — 파일 자체를 버전으로 두는 편이 리뷰·재현이 쉽다 |
| 행마다 INSERT | 2,700행 × 4,900단위 = 왕복 1,300만 번. COPY 는 단위당 1번 |

## 결과
- 화면 성능·기능은 그대로, 분석은 전 종목·10년으로 넓어졌다. 적재가 중간에 끊겨도 이어서 받는다.
- 감수한 점: 두 계층에 같은 종목 정보가 따로 있다 — 이름·업종은 `security_master` 를 기준으로 맞춘다.
  마이그레이션 파일은 한 번 배포되면 고칠 수 없어 실수도 새 파일로 바로잡아야 한다.

## 검증
```bash
.venv/bin/python run.py platform-load --years 10 --budget 5000   # 백필(여러 번 실행 = 이어 받기)
.venv/bin/python run.py platform-status                          # 행 수·파티션·커버리지·적재 이력·마이그레이션
.venv/bin/python -m pytest -q tests/test_platform.py
```
(데이터 현황 화면은 2026-10-20 기각 — 같은 내용을 `run.py platform-status` 가 출력한다.)
