# ADR-0016 이상거래탐지는 설명 가능한 규칙 점수로(평가를 함께), 후속 처리는 트랜잭셔널 아웃박스로

| 항목 | 내용 |
|---|---|
| 상태 | 채택 · 2026-10-20 · **개정 2026-10-24**(정밀 점검 결함 20·21·22·26 — 아래 '개정') |
| 범위 | 데이터 처리 — 사기 방지 · 일관성 |
| 코드 | `app/services/fds.py`(features·score·screen·record) · `transfer.py`(판정 위치) · `outbox.py` · 스케줄러 30초 중계 · `/admin/fds` |
| 시험·평가 | `test_fds.py` · `test_outbox.py` · `python run.py fds-eval` → `docs/models/fds_eval.md` |

## 맥락
송금이 생기자 '계정 탈취 후 인출'·'대포 계좌 집금'·'충전 후 즉시 이체' 같은 수법을 막을 장치가 필요했다. 라벨 데이터가 없어
학습 모형은 근거가 약하다. 또 송금 뒤 알림을 같은 요청에서 바로 보내면, 알림은 갔는데 거래가 롤백되거나 그 반대가 생긴다(이중 쓰기).

## 결정 — FDS
- 송금 트랜잭션 안(두 지갑 잠금 뒤) 규칙 10개 점수 합: 속도(10분 5건 +40) · 급증(중앙값 5배 +25) · 잔액 소진(+20) · 처음 받는 사람 고액(+20) ·
  세션 IP 대역 변경(+20) · 24시간 내 비밀번호 변경(+15) · 받는 사람 집금(1시간 5명 +35) · 왕복(+20) · 충전 후 송금(+25) · 새벽 고액(+10).
- **70점 이상 차단 · 40점 이상 추가 인증** — 정책(PDP)의 추가 인증과 같은 길을 쓴다. 판정은 `fds_decision` 에 남겨(1년) 오탐 검토.
- 점수 함수는 순수 함수(DB 없이 평가) — 합성 2만 건(사기 10%): 탐지 100% · 사기 차단 85% · **정상 차단 0.05%** · 정상 추가 인증 4.8%.

## 결정 — 아웃박스
- 업무 트랜잭션 안에서 `outbox` 에 사건을 적는다 → 롤백되면 사건도 없다.
- 중계기(30초)가 `FOR UPDATE SKIP LOCKED` 로 골라 **리스로 빌린 뒤 트랜잭션 밖에서** 처리(중계기가 여럿이어도 중복 없음), 실패하면 2^n 초 뒤(최대 1시간), 8번째 실패면 dead.
- 처리기: `transfer.completed` → 고액 송금 모니터링 알림. 실시간 화면 알림은 커밋 시점 `pg_notify`(ADR-0017).

## 검토한 대안
| 대안 | 버린 이유 |
|---|---|
| 지도 학습 모형 | 라벨 없음 · 설명 불가(왜 막혔는지 고객에게 말할 수 없다) — 운영 기록이 쌓이면 규칙 가중치 보정부터 |
| 차단만(추가 인증 없음) | 오탐이 곧 고객 피해 — 중간 단계(추가 인증)가 마찰을 줄인다 |
| 메시지 브로커(Kafka 등) | 규모 대비 과함, 결국 DB 와의 이중 쓰기 문제는 그대로 — 아웃박스가 표준 해법 |

## 결과와 한계
- 합성 분포 수치는 실제 성능이 아니다(알려진 수법의 회귀 시험 용도). 왕복 거래는 탐지 100% 이지만 차단은 40.5%(나머지는 추가 인증).
- E2E 에서 '새 계정이 처음 보는 사람에게 환영금을 거의 다 보내는' 정상 시나리오가 추가 인증 등급으로 걸리는 것을 확인 — 의도된 마찰.

## 개정(2026-10-24) — 판정과 실행 사이에 틈이 없게, 전달은 정말 '최소 1회'로
| 결함 | 문제(옛 코드로 재현) | 바꾼 것 |
|---|---|---|
| 20 | **TOCTOU** — API 가 지갑 잠금 '밖'에서 먼저 채점 → 동시에 보낸 10건이 모두 '최근 10분 0건'을 보고 통과(속도 규칙 무력화) | 판정을 송금 트랜잭션 안, **두 지갑 잠금 뒤**로 — 같은 사람·같은 받는 사람의 송금은 잠금에서 줄을 서 앞 송금이 반영된 상태로 채점(동시 10건 → 5건 실행·5건 추가 인증) |
| 21 | 멱등 재시도를 판정보다 늦게 확인 → 이미 처리된 송금을 다시 채점해 4xx(추가 인증·차단) → 화면은 4xx 면 새 키를 만들어 **같은 돈을 한 번 더** 보낼 수 있었다 | 순서 고정: 계정 확인 → 지갑 잠금 → **같은 키 처리 여부** → 판정 → 실행. 처리된 재시도는 채점 없이 처음 결과(`duplicate:true`) |
| 22 | 받는 사람 앞뒤 공백 — 실행은 정규화한 계정, 판정은 원문(행 없음)으로 → 집금(fan_in)·왕복 규칙 회피 | 입구(요청 모델)에서 한 번 정규화, 판정·실행·감사가 같은 값 |
| 26 | 아웃박스 처리기를 꺼낸 트랜잭션 안에서 실행 — 전송이 길면 유휴 트랜잭션 제한(60초)에 끊겨 묶음 롤백·재전송, 처리기 안의 전송 실패는 삼켜져 '완료'(유실) | **리스(lease) 방식**: 짧은 트랜잭션으로 빌리고(시도+1·리스 5분) 바로 커밋 → 처리기는 트랜잭션 밖 → 사건마다 완료/재시도. 채널 전부 실패면 예외(재시도), 사건 키로 72시간 중복 억제 |

**통제 완전성(탐지 통제)** — 실행된 송금과 판정은 같은 트랜잭션에서 커밋되고 `fds_decision.ref` = 송금 키로 잇는다.
데이터 계약 `wallet.transfer_unscreened`(critical)가 매일 '최근 30일, 판정 없이 실행된 송금 0건'을 확인 — 나중에 누가 판정을 거치지 않는
송금 경로를 만들어도 다음 날 드러난다. 막힌 시도(추가 인증·차단)는 롤백 뒤 따로 기록된다.
