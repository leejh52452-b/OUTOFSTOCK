## 맥락
서버는 단일 VM(워커 1~4)이다. 지금까지는 '얼마나 버티나'(부하 시험 185 RPS)만 쟀고, **넘쳤을 때 무엇을 먼저 지키나**는 정하지 않았다.
측정해 보니 공개 시세 조회가 몰리면 핵심 거래(로그인 유지·송금)도 같은 줄에 서서 함께 느려졌고(p50 0.7초), DB 연결 풀이 다 차면
기본 30초를 기다린 뒤 500 이 났다. 돈의 정합성이 깨졌을 때(원장 변조·마감 실패) 그 기능을 멈추는 수단도 없었다 — 알림만 갔다.

## 결정
1. **임계치 4단계** — 지표: 워커별 동시 처리 요청(SSE 긴 연결 제외)·DB 연결 사용률·최근 1분 p95 지연·5xx 비율.
   비율 0.6/0.8/0.95(`CAPACITY_RATIOS`), 지연 500/1000/3000ms(`CAPACITY_P95_MS`), 5xx 1/5/20%. 단계 = 지표별 단계 중 가장 나쁜 것.
2. **우선순위 대량접속제어** — 경로마다 중요도: policy.json 동작의 `tier`(critical·normal·low, 경로 예외는 `admission.routes`).
   경계면 low(공개 시세·뉴스·추천), 심각이면 normal(조회·학습)까지 **즉시 503 + Retry-After** — 경로 의존성(세션·DB)보다 먼저 거절해
   스레드·연결을 쓰지 않는다. critical(로그인·갱신·송금·결제·구매·탈퇴·관리·헬스)은 끝까지 받는다.
   **입장 판단은 즉시 값(동시 요청·연결 사용률)만** — 지연·오류율로 막으면 막을수록 지연이 줄어 다시 여는 진동이 생긴다(지연·오류는 보고 단계에만).
3. **성능관리보고서** — 보고 단계가 경계·심각으로 올라가면(같은 단계 10분에 1번) 그 순간 지표·느린 경로 5개·돌려보낸 건수·권고를
   `capacity_report` 에 남기고 운영 알림. `/admin/capacity`(운영 관제 역할) · Prometheus 게이지(`oos_capacity_level` 등).
4. **연결 풀 빠른 실패** — `pool_timeout` 30초 → 5초(`DB_POOL_TIMEOUT_S`), 초과하면 500 이 아니라 503(Retry-After 3) + 지표.
5. **서비스 비상 차단** — 기능 4개(송금·충전·꾸미기 구매·모의투자 = 동작의 `control`). 보안·운영 관리자(JIT·OTP) **한 사람이 즉시 멈춘다**
   (사고 때는 빨라야 한다). **다시 여는 것은 재개 요청 + 다른 관리자 승인**(요청자 ≠ 승인자 — 원인 확인 없이 한 사람이 여는 것을 막는다).
   멈춘 기능은 PEP 가 503(`service_paused`) — 조회·다른 기능은 그대로. 상태는 워커별 2초 캐시. 모든 변경은 감사 체인 + 보안 이벤트 + 알림.
   **자동 차단 규칙**: 원장 변조 탐지·원장 마감 실패(대사 불일치) → 돈이 오가는 4기능 중지, FDS 차단 10분 10건 → 송금 중지.
6. **요청당 SQL 예산** — 측정: 송금 한 건이 같은 계정 잠금 5번·지갑 확인 4번·계좌번호 조회 4번(SQL 41개), 지갑·꾸미기 조회(GET)가
   매번 계정 잠금 + `INSERT … ON CONFLICT`(조회가 쓰기). → 트랜잭션 범위 메모(`db.tx_cache` — Connection 객체에 붙어 트랜잭션과 함께 사라짐)로
   같은 트랜잭션의 반복 제거, 조회는 '있으면 SELECT 한 번'. 송금 41 → 33, 지갑 조회 5 → 3(쓰기 0), 출석 20 → 16. 예산을 시험으로 고정.

## 검토한 대안
| 대안 | 버린 이유 |
|---|---|
| nginx `limit_conn`·`limit_req` 만 | 경로의 '중요도'를 모른다(같은 IP 의 로그인과 시세 조회를 같이 깎는다). 경계 방어로 유지하고, 앱이 중요도로 한 번 더 |
| 지연 기반 적응형 한도(AIMD·CoDel) | 단일 VM·워커 1~4 규모에선 설명·검증이 어려운 진동 위험. 임계치 4단계(가이드라인과 같은 언어)가 운영자에게 읽힌다 |
| 차단 중 low 요청에 옛 캐시 응답 | 표시 기준일이 섞인다(이 서비스는 '언제 값인지'를 화면에 적는다). 503 + 화면 안내가 정직하다 |
| 재개도 한 사람 | 사고 원인을 확인하지 않고 다시 여는 것이 가장 흔한 2차 사고 경로 — 멈춤은 빠르게, 재개는 2인 |
| 기능 스위치를 설정 파일·환경변수로 | 바꾸려면 재시작·배포가 필요하고 누가 왜 바꿨는지가 남지 않는다 — DB 상태 + 감사 체인 |

## 결과(측정 — `docs/perf/overload_test_2026-11-02.md`)
같은 서버(1 worker, 동시 한도 24)·같은 부하(공개 조회 60 클라이언트 + 핵심 거래 4 클라이언트, 20초)에서 대량접속제어만 켜고 끔:

| | 끔 | 켬 |
|---|---:|---:|
| 핵심 거래(토큰 갱신) p50 / p95 / p99 | 718 / 899 / 986 ms | **216 / 354 / 428 ms** |
| 핵심 거래 처리 수 · 성공률 | 66건 · 100% | **199건(3배)** · 100% |
| 공개 조회 처리 · 즉시 거절(503) | 1,139 · 0 | 770 · 2,047 |

공개 조회의 일부를 즉시 돌려보낸 대가로 핵심 거래 지연이 약 1/3, 처리량이 3배. 성능관리보고서는 경계·심각 진입마다 자동 기록됐다.

## 한계
- 워커별로 센다(공유 카운터 없음) — 워커가 여럿이면 한도 × 워커 수가 서버 한도. 연결 예산(워커 × 풀 30 + 배치)은 DB `max_connections` 안에서 정한다.
- 비상 차단 상태는 워커별 2초 캐시 — 멈춘 뒤 최대 2초 동안 다른 워커가 받을 수 있다(돈 동작 자체는 원장·FDS·멱등이 여전히 지킨다).
