## 맥락
RLS 도입 뒤 매일 백업이 **조용히 실패**하고 있었고(일반 계정 `pg_dump` 가 FORCE RLS 에 막힘), 백업 파일은 평문이었으며,
복원해 본 적이 없었다. 덮어쓰기 복원(`--clean`)은 분할 표 제약에서 실패해 반쯤 복구된 DB 를 남겼다.

## 결정
- **일관 스냅샷** — `pg_export_snapshot` + `pg_dump --snapshot`(행 수·체인 머리를 같은 시점에서). 백업 전용 계정(읽기 전용 + BYPASSRLS).
- **암호화** — age 공개키(수신자 2개: 운영·금고). 서버엔 공개키만, 덤프는 파이프로 바로 암호화(평문 파일 없음).
- **manifest** — 암호문·덤프 SHA-256, 표별 행 수, 감사·원장 체인 머리, RLS·정책·트리거 수, 스키마 버전, 데이터 품질 기준선.
- **복원은 새 DB 에** → 검증 8항목(표별 행 수 · 감사 체인 · 외부 증인 · 원장 마감 사슬과 시산표 · 데이터 계약 · 암호문 키 링 · RLS·정책·트리거 · 스키마 버전) 통과 시에만
  이름 두 개를 한 트랜잭션으로 교체. 실패하면 운영 DB 그대로.
- **훈련 자동화** — 격리 DB 에 복원·검증·서비스 기동 점검·RTO/RPO 실측 보고서. 92일 넘게 훈련이 없거나 26시간 넘게 백업이 없으면
  관리자 헬스 경보(공개 헬스에는 숨김).
- **보관** — 최근 14개 + 월별 12개(GFS), 원격 사본 명령(셸 없이).
- **PITR(선택)** — WAL 보관(gzip + age) + 베이스 백업 + `pg_verifybackup` · 시점 복구 훈련 스크립트.

## 검토한 대안
| 대안 | 버린 이유 |
|---|---|
| `pg_dump` 크론 + 평문 | 실패를 모르고, 유출되면 전체 개인정보 |
| 덮어쓰기 복원 | 실패 시 반쯤 복구된 DB(실제로 발생) |
| 물리 백업만 | 버전·플랫폼에 묶이고 부분 복원이 어렵다 — 논리(매일) + PITR(선택) 병행 |

## 결과(실측)
- 훈련 RTO 2.3~2.7초(0.8MB · 75표 · 3만 행) · VM 복원(교체 포함) 6.8초 · PITR 7.9초 — 전자금융감독규정 제23조의 핵심업무 3시간에
  비해 여유가 크지만, **데이터가 커지면 다시 잰다**(보고서 자동 생성).
- 발견해 고친 것 7건(빈 백업 탐지·스냅샷 일관성 등) — `docs/dr/README.md`.
