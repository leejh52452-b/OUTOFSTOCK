# ADR-0017 실시간 알림은 폴링 대신 SSE — 커밋된 것만 보내는 PostgreSQL LISTEN/NOTIFY 위에

| 항목 | 내용 |
|---|---|
| 상태 | 채택 · 2026-10-20 |
| 범위 | 성능 · 정합성 |
| 코드 | `app/services/stream.py` · `GET /events` · nginx `location = /events`(버퍼링 끔) · 화면 `sseStart()`(실패 시 폴링으로) |
| 시험 | `test_stream.py` · E2E ④(다른 사람의 송금이 새로 고침 없이 반영) · 부하 시험 3-4 |

## 맥락
채팅·지갑·친구 알림을 2초마다 물었다(사용자당 분당 30요청). 대부분 '변화 없음' 응답이고, 세션 확인·RLS 문맥 비용이 요청마다 든다.

## 결정
- 업무 트랜잭션 안에서 `pg_notify` — PostgreSQL 은 **커밋될 때만** 알림을 보낸다(롤백된 송금의 잔액 알림 없음).
- 워커마다 리스너 1개(전용 연결)가 LISTEN 하다 그 워커의 사용자 스트림에 나눠 준다. 워커·서버가 여럿이어도 DB 가 모두에게 뿌린다.
- 스트림은 세션 주인에게만, 20초마다 keep-alive, **30분이면 끊고 다시 연결**(그때 세션을 다시 확인), 세션이 폐기되면 즉시 종료.
- 화면은 SSE 가 살아 있으면 채팅 폴링을 15초로 늦추고, 끊기면 2초 폴링으로 돌아간다(점진 저하).
- nginx 는 `/events` 만 버퍼링을 끄고 읽기 시간 제한 1시간.

## 검토한 대안
| 대안 | 버린 이유 |
|---|---|
| 웹소켓 | 양방향이 필요 없고, 쿠키·CSRF·프록시 설정이 더 복잡하다 |
| 폴링 주기 늘리기 | 채팅 체감 지연이 커진다 |
| Redis Pub/Sub | 인프라 추가 + 커밋과 알림 사이 불일치(이중 쓰기) |

## 결과
- 20초·사용자 10명 기준 요청 100 → 10(사용자당 연결 1개).
- 연결을 오래 쥐므로 워커당 동시 연결 수가 늘어난다 — uvicorn 비동기 처리로 감당, nginx `limit_conn` 60/IP 안.
