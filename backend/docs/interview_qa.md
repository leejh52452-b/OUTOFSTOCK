# 면접 Q&A 뼈대 — OUTOFSTOCK 데이터·백엔드

쓰는 법: 각 축마다 ① 30초 설명 ② 예상 질문과 답의 뼈대(숫자는 `docs/verification.md` 대로 VM 에서 다시 잰 실데이터 값으로 바꿔 넣기)
③ 꼬리 질문 대비. 합성·표본 결과는 반드시 "파이프라인 검증용 합성 데이터"라고 말한다. 규정은 '준수'가 아니라 **설계 기준**이라고 말한다
(이 서비스는 전자금융업자·공공기관이 아니다).

## 0. 전체 한 문장
"주식 학습 앱의 데이터·백엔드를 맡아, 서비스 표와 분리된 **전 종목 × 10년 분석 계층** 위에 **신용위험 모형·수익률 예측 검증**을 얹고,
가상머니를 **복식부기 원장·이상거래탐지·아웃박스**로 처리했습니다. 보안은 금융권 기준(안전성 확보조치·전자금융감독규정·N²SF)을
설계 기준으로 **제로트러스트**(매 요청 세션 재확인·정책 엔진·행 단위 보안·봉투 암호화·감사 해시 체인)로 옮겼고, 백업은 **복원해서 검증된 것만**
백업으로 칩니다. 화면은 팀 시안 그대로 두고, 쓰지 않는 기능의 API 55개를 지워 공격 표면을 31% 줄였습니다."

## 1. 장애 대응(ADR-0001)
**30초**: 설치 직후부터 매일 시세 적재가 마지막 단계에서 롤백됐는데, 로그에만 남아 사용자가 빈 화면을 보고서야 알았습니다.
원인(메타값 VARCHAR 한도)을 재현·수정한 뒤, '예외 없이 끝남 ≠ 성공'이라는 교훈으로 기대치 비교 게이트와 다중 채널 알림을 붙이고 장애 보고서를 썼습니다.
- Q. 원인을 어떻게 찾았나? → VM 진단 결과(유니버스·연속 일봉·적격 종목 수)를 숫자로 받고, 같은 상태를 로컬에 재현해 `StringDataRightTruncation` 확인. 고치기 전 스키마에서 실패하는 회귀 테스트부터.
- Q. 품질 게이트 항목은? → 출처·완전성(유니버스 90%)·이력 깊이(60봉 종목 90%)·적시성(1거래일 warn, 2거래일 fail)·상식(종가 ≤0, ±30% 초과).
  이후 **데이터 계약**(데이터셋별 기대치 표 — `run.py dq`)으로 넓혀 매일 배치에 넣었다.
- Q. 알림 폭주는? → 같은 key 6시간 중복 억제, 비밀값 가림, 채널 실패가 배치를 멈추지 않음.
- 꼬리: "왜 원자적 트랜잭션이 오히려 피해를 키웠나?" → 원자성 덕에 잘못된 값은 안 들어갔지만(데이터 손실 0), 정상 수천 행까지 함께 롤백. 그래서 적재 단위를 쪼개고(2번) 검증을 붙였다.
- 꼬리: BCBS 239 → 완전성·적시성을 '측정 가능한 기대치'로 바꾼 것이 게이트(원칙 3·4·5 — `docs/security/compliance_mapping.md` §4).

## 2. 데이터 플랫폼(ADR-0002·0003·0004·0010)
**30초**: 화면용 150종목 표와 분리된 analytics 스키마에 전 종목 × 10년(약 670만 행)을 쌓았습니다. 적재는 (거래일, 시장) 단위로
재개 가능하게, COPY + 병합으로 멱등하게 만들었고, 인덱스는 같은 700만 행에서 4가지 구성을 EXPLAIN 으로 재서 골랐습니다.
- Q. 왜 파티션? → 질문이 '최근'에 몰려 있어 연도 파티션이면 최근 1년 쿼리가 1~2개 파티션만 읽는다. 오래된 해는 DETACH.
- Q. 인덱스는 어떻게 골랐나? → (실측) 최신 거래일: 파티션 없음 504ms / 파티션만 819ms(더 느림!) / +B-tree 0.03ms / +BRIN 777ms.
  그날 순위: 208 → 33 → 0.71 → 0.72ms. BRIN 은 180배 작지만 max 에 못 써서 B-tree.
- Q. 파티션만 했는데 왜 느려졌나? → 날짜 조건 없는 max 는 11개 파티션을 다 훑는다. 최신일을 CTE 로 조인하면 계획 시점에 값을 몰라 전 파티션 스캔 → 스칼라 서브쿼리로 넘겨 실행 시점 파티션 제외.
- Q. 10년 백필 중 끊기면? → load_log 에 단위별 ok/empty/failed + 원천 체크섬. 다시 실행하면 끝나지 않은 단위만. 호출 예산으로 하루 한도 안에서.
- Q. 분석 쿼리의 안전은? → 이름 있는 SQL 파일만, 파라미터는 파일 머리에 선언된 형식·범위만, 읽기 전용 계정 + 읽기 전용 트랜잭션 + 5초 제한.
  화면 분석 API 는 기능을 접으며 지웠고 지금은 CLI(`run.py analytics-query`) 전용 — 계정계(서비스)와 정보계(분석)의 분리.
- Q. 수정주가는? → 5:1 액면분할 날을 −80% 로 보던 결함. KRX 등락률은 기준가 대비라 원 종가 비율과 다르면 그날이 권리 이벤트, 비율이 조정계수.
  원 가격은 그대로 두고 계수를 따로 저장해 읽을 때 곱한다(원천 보존 — 감사 추적). 봉이 빠진 날을 이벤트로 오인하던 오탐은 시장 달력으로 막았다.
- 꼬리: "ClickHouse 같은 컬럼 DB 는?" → 700만 행·단일 VM 에서 운영 대상을 늘릴 이유가 측정상 없었다. 10배 커지면 재검토.

## 3. 데이터 거버넌스 — 분류·사전·계보·품질(BCBS 239 원칙 2·3)
**30초**: 모든 표를 등록부에 **등급(공개·내부·개인·민감)·보관 기간·RLS·암호화 여부**와 함께 선언하고, 그 등록부에서 데이터 사전과
계보 문서를 자동으로 만듭니다. 문서와 코드가 어긋나면 시험이 실패해 '문서가 낡는 문제'를 구조로 막았습니다.
- Q. 등록부가 실제 DB 와 같은지 어떻게 아나? → 시험이 등록부의 RLS 표시 = DB 의 FORCE RLS, 암호화 표시 = 암호화 열 목록을 대조(`test_data_protection.py`·`test_datadocs.py`).
- Q. 보관 기간은 누가 지우나? → 매일 파기 작업(`run.py security-purge`). 2025.10.31 개정 안전성 확보조치 기준 제5조③ 에 맞춰
  **권한 부여·변경·말소 기록은 3년 하한**을 코드에 박았다(설정을 줄여도 1095일 미만으로 안 지움). 탈퇴자의 관리 권한 내역은 지우지 않고 가명으로.
- Q. 가명정보는? → `run.py export-pseudonymized` — k-익명성(기본 5) 검사 후 일반화 단계를 올리고, 부족한 그룹은 억제. 목적 기재 필수.
- 꼬리: "이게 왜 데이터 직무와 관련?" → 정책금융 데이터는 '어디서 왔고 누가 바꿨나'를 설명해야 한다. 계보·사전·품질 지표가 그 근거.

## 4. 원장·이상거래탐지·아웃박스(ADR-0015·0016) — 돈이 오가는 데이터 처리
**30초**: 가상머니를 잔액 컬럼 갱신이 아니라 **복식부기 분개**로 바꿨습니다. 거래마다 차변·대변 합이 0 인 것을 DB 제약이 강제하고,
매일 마감 해시를 앞날과 사슬로 묶어 사후 변조를 잡습니다. 송금 직전에는 설명 가능한 규칙 점수(FDS)로 허용·추가 인증·차단을 정하고,
후속 처리(알림·모니터링)는 같은 트랜잭션의 아웃박스에 적어 '돈은 옮겼는데 알림은 누락' 같은 불일치를 없앴습니다.
- Q. 합 0 을 어떻게 강제? → 분개 행 삽입 뒤 트랜잭션 끝에서 검사하는 지연 제약 트리거 — 앱이 실수해도 커밋이 안 된다. 원장 행은 UPDATE/DELETE 금지.
- Q. 대사는? → 일 마감 때 지갑 잔액 = 원장 합, 시산표 0, 앞날 마감 해시 연결. `run.py ledger-verify`. 복원 훈련도 이 검사를 한다(백업이 회계적으로 온전한가).
- Q. FDS 를 왜 머신러닝이 아니라 규칙으로? → 라벨이 없고, 차단 사유를 고객·감사에 설명해야 한다. 규칙 10개(10분 안 연속 송금·평소의 5배·잔액 소진·첫 수취인 고액·
  세션 IP 대역 변경·24시간 안 비밀번호 변경·수취인 집금·왕복·충전 직후 이체·새벽 고액) 점수 합 **40 이상 추가 인증, 70 이상 차단**.
- Q. 평가는? → 합성 2만 건(사기 10%, 5가지 수법) — 사기 탐지 100%, **정상 거래 차단 0.05%**(가장 중요한 오탐), 정상 추가 인증 4.8%. 실제 성능이 아니라 회귀 시험 용도라고 말한다.
- Q. 아웃박스가 왜 필요? → 송금 커밋 후 알림을 바로 보내면, 커밋은 됐는데 알림이 실패하거나(누락) 롤백됐는데 알림이 나간다(유령). 같은 트랜잭션에 '보낼 일'을 적고
  30초 중계기가 꺼내 보낸다(최소 1회 + 멱등 키). 실시간 화면 알림(SSE)도 PostgreSQL NOTIFY 가 '커밋될 때만' 나가는 성질을 이용.
- 꼬리: 멱등키 → 같은 `Idempotency-Key` 재전송은 처음 결과를 돌려주고(더블클릭·재시도), 같은 키로 금액을 바꾸면 409.
- Q. 직접 찾아 고친 결함 중 하나만? → **FDS 판정과 실행 사이의 TOCTOU**. 판정을 지갑 잠금 '밖'에서 먼저 하니, 같은 계정에서 송금 10건을 동시에 보내면
  10건 모두 '최근 10분 0건'을 보고 통과했다(속도 규칙 무력화 — 옛 코드로 재현). 판정을 송금 트랜잭션 안, 두 지갑을 잠근 뒤로 옮겨 동시 송금도 줄을 서서
  채점된다(10건 → 5건 실행·5건 추가 인증). 같은 김에 순서를 '같은 키 처리 여부 → 판정'으로 고정 — 응답을 못 받은 재시도가 다시 채점돼 4xx 를 받고
  화면이 새 키로 한 번 더 보내는 **이중 송금** 경로도 닫았다.
- Q. 통제가 우회되지 않았다는 건 어떻게 아나? → 실행된 송금과 판정을 같은 트랜잭션에 커밋하고 송금 키로 잇는다. 데이터 계약이 매일 '판정 없이 실행된 송금 0건'을
  확인한다 — 예방 통제(판정) 위에 **탐지 통제(완전성 대사)**. 나중에 누가 판정을 거치지 않는 경로를 만들어도 다음 날 드러난다.
- Q. 마감 해시는 무엇을 덮나? → 처음엔 합계(건수·차변·대변·계정별 합)만 덮어, 합계를 유지한 채 거래 사이에서 금액을 옮기는 변조를 못 잡았다(재현).
  지금은 분개 한 줄 한 줄의 SHA-256 다이제스트까지 덮고, 마감 해시를 감사 해시 체인(외부 증인)에도 같은 트랜잭션으로 남긴다 — DB 소유자가 분개와 마감 기록을
  함께 다시 계산해 넣어도 감사 체인과 달라 드러난다. 서버가 꺼져 있던 날은 다음 실행이 날짜순으로 메우고, 검증은 빠진 날을 따로 보고한다.
- Q. 보상(퀴즈 정답 10만 원)을 '하루 1번'만 주는 건? → 앱의 '오늘 받았나?' 확인은 동시 요청 둘이 모두 '아니오'를 볼 수 있다(TOCTOU).
  퀴즈 기록에 보상 날짜를 넣고 (계정, 보상 날짜) **부분 유일 인덱스** — 대상 없는 `ON CONFLICT DO NOTHING` 이 문제 날짜 PK 와 함께 처리해
  동시 요청은 앞 트랜잭션 결과를 기다렸다 판단한다. 지급(지갑·원장·분개)은 기록과 같은 트랜잭션(지급 실패 = 기록 롤백). 4스레드 동시 제출 → 지급 1번(`test_quiz.py`).
- Q. 양봉이 꾸미기(ADR-0022) — 아이템 가격을 화면이 보내면? → 화면은 아이템 id 와 '보여 준 가격'만 보내고, 서버는 카탈로그 사본의 가격으로 뺀다.
  둘이 다르면 409 로 아무것도 바꾸지 않는다(캐시된 옛 화면이 1만원이라 보여 주고 1억을 빼는 일 방지 — 동의한 금액 = 빠지는 금액).
  카탈로그는 화면 파일 하나(그림·이름·가격)이고 서버 사본은 도구로 꺼내 원본 해시를 시험이 비교한다.
- Q. 두 탭에서 동시에 사면? 부위당 하나만 입게 하는 건? → 산 기록(계정·아이템 PK, `ON CONFLICT DO NOTHING`)·지갑 차감(멱등키)·착용을 한 트랜잭션 +
  계정별 advisory lock — 5스레드 동시 구매 → 차감 1번, 잔액 부족이면 기록도 롤백. 착용은 `(계정, 부위) WHERE equipped` 부분 유일 인덱스가 DB 에서 보장.
- Q. 아웃박스 처리기는 어디서 도나? → 트랜잭션 '밖'. 짧은 트랜잭션으로 사건을 빌리고(리스 5분, 시도 +1) 바로 커밋한 뒤 외부 전송 → 사건마다 완료/재시도.
  예전엔 꺼낸 트랜잭션 안에서 전송해, 느린 웹훅이 유휴 트랜잭션 제한에 걸리면 묶음 전체가 롤백·재전송됐고, 전송 실패는 삼켜져 '완료'로 남았다.

## 4-1. 운영 복원력·탈취 내성(ADR-0023·0024, 2026-11)
- Q. 트래픽이 몰리면? → 금감원 「금융IT 안정성 강화 가이드라인」(2023.11)의 성능 관리 언어 그대로 — 임계치 4단계(정상·주의·경계·심각)를
  동시 요청·DB 연결 사용률·p95·5xx 로 판정하고, **경계면 공개 시세·뉴스, 심각이면 일반 조회까지 503**으로 먼저 돌려보낸다(경로 의존성보다 먼저 —
  DB·스레드를 안 씀). 로그인·갱신·송금·결제·관리는 끝까지 받는다. 같은 부하에서 켜고 끄며 재 보니 핵심 거래 p95 899 → 354ms, 처리량 3배.
- Q. 지연이 높으면 막으면 되지 않나? → 막을수록 지연이 줄어 다시 여는 **진동**이 생긴다. 입장은 즉시 값(동시 요청·연결)으로만, 지연·오류율은 보고·경보에만.
- Q. 경계·심각이 되면 누가 아나? → 그 순간의 지표·느린 경로 5개·차단 건수·권고를 담은 성능관리보고서를 자동으로 남기고 알림(같은 단계 10분 1번) —
  가이드라인의 '경계·심각 시 성능관리보고서를 CIO 에게 지체 없이'를 시스템이 대신 쓴다.
- Q. 사고가 나면 송금을 어떻게 멈추나? → 기능별 비상 차단(송금·충전·구매·모의투자). 관리자 한 사람이 사유를 적고 즉시 멈추고, 원장 변조·마감 실패·FDS 차단 급증은
  시스템이 자동으로 멈춘다. **다시 여는 것은 재개 요청 + 다른 관리자 승인** — 원인 확인 없는 재개가 2차 사고의 흔한 경로라서. 조회·다른 기능은 그대로.
- Q. 쿠키를 훔치면? → HttpOnly 라 XSS 로는 못 읽지만 PC 감염·확장 프로그램이면 통째로 복사된다. 그래서 세션을 브라우저 안의 **꺼낼 수 없는 ECDSA 키**에 묶었다
  (RFC 9449 DPoP 방식). 갱신·돈·관리 요청마다 그 키의 1회용 서명이 필요해, 쿠키만 가진 다른 기기는 송금 401·갱신 시 세션 종료(실제 브라우저 E2E).
  표준 예시 키의 지문이 RFC 값과 일치하는지 시험으로 확인했다.
- Q. 성능 개선 하나만? → 요청당 SQL 을 세어 봤더니 송금 한 건이 같은 계정 잠금을 5번·계좌번호 조회를 4번(41문장), 지갑 '조회'가 매번 INSERT 를 했다.
  트랜잭션 범위 메모로 같은 트랜잭션의 반복을 없애고 조회는 SELECT 한 번 → 송금 33, 지갑 조회 3(쓰기 0). 예산을 시험으로 고정해 N+1 회귀를 막는다.
- Q. 채팅에 주민번호를 쓰면? → 저장(암호화) 전에 가린다 — 생년월일이 실제 날짜 + 성별 자리, 카드는 룬 검사로 오탐을 줄였다. 가린 사실만 이벤트(내용 없음).

## 4-2. 자율보안 — 금융보안 수준진단·위험 등록부·파일 무결성·훈련(ADR-0025, 2026-11)
- Q. 보안 수준을 어떻게 아나? → 금융보안원 「금융보안 수준진단 프레임워크」(2026.2 — 7개 분야 45개 항목)로 스스로 진단한다. 등급(초기·기반·발전·고도화)은
  **사람이 매기지 않고 근거 종류로 판정** — 문서 + 구현이면 기반, + 자동 시험 + 운영 점검이면 발전, + 자동 대응 + 실측 기록이면 고도화. 근거는 기계가 확인한다
  (파일·함수·시험 이름은 구문 트리, 탐지 규칙·스케줄 작업은 등록 여부). 시험을 지우면 등급이 내려가고 CI 가 실패한다.
- Q. 자율보안의 약점이 '검증 어려움'인데? → 그래서 모든 주장에 기계가 확인하는 근거를 걸었다. 운영 모드에선 프로브 15종(감사 체인·원장·RLS·정책·설정 기준선·
  암호화·백업·훈련·부하·파일 무결성·휴면 권한·위험 등록부 등)을 실제로 돌려, 실패한 항목은 '기반'으로 내린다. 결과는 추가만 저장되고 다이제스트가 감사 체인에 남는다.
- Q. 결과는? → 같은 엔진으로 개선 전 기준선을 먼저 쟀다: **2.93 → 3.21**(4점 만점), 목표 미달 9 → 0, CSF 2.0 근거 하위 항목 67 → 76/106.
  가장 약했던 공급망(2.0)·식별(2.2)부터 고쳤다 — 위험 처리(초기 → 발전)·파일 모니터링(초기 → 발전)·공급사 선정 기준(초기 → 발전). 금융보안원 발표로는 평균적인
  금융회사가 2단계, 국내 대형사가 평균 3단계라고 하지만, **판정 규칙이 자체 기준이라 직접 비교하지 않는다**고 문서에 적었다.
- Q. 위험 평가는? → 특강의 자율보안 4단계 그대로 — 자산 식별·중요도(C·I·A 점수, 코드에서 자동) → 위협 시나리오(위협 모델 T-01~35) → 가능성×영향(고유·잔여) →
  처리·담당·재검토. 위험 성향 9를 넘는 잔여는 계획+기한 또는 승인 수용이 없으면 시험이 실패한다. 위협 모델이 '이 시험으로 막았다'고 적은 시험 56건이 실제로 있는지도 검사한다.
- Q. 웹셸은? → 배포 직후 파일별 SHA-256 기준선을 **소유자 계정만** 기록하고(앱 계정은 읽기만), 10분마다 비교해 바뀐·사라진·**새 파일**을 심각 경보.
  앱 권한을 얻은 공격자는 기준선을 못 고친다. DB 소유자가 기준선 행을 고쳐도 다이제스트가 맞지 않아 위반.
- Q. 퇴사자 계정은? → 전자금융감독규정 제13조 ①11호 — 인사조치 한 번으로 자격·활성 권한·대기 요청·세션을 회수하고 계정을 중지한다. 60일 동안 한 번도 켜지 않은
  관리 자격은 매일 자동 회수(금감원 검사에서 흔한 '퇴직자·장기 미사용 계정' 지적을 코드로 막는다).
- Q. 사고 대응 훈련은? → 5개 시나리오(원장 변조·이상 송금 급증·대입 공격·쿠키 탈취·파일 변조)를 격리 DB 에서 자동으로 — 신호 → 탐지 → 자동 차단 → 실제 요청이
  막히는지 확인 → 2인 재개. 단계별 시간을 기록했다(자동 차단 23~85ms). 운영 알림 채널로는 보내지 않고, 이용자가 있는 DB 에서는 시작을 거부한다.

## 4-3. IT 내부통제 — 변경관리·장애 판정·사고보고·관제·취약점 자가 점검(ADR-0026, 2026-11)
- Q. 금융권 공기업 지침에서 무엇을 가져왔나? → 2026년 당국이 짚은 IT 사고 원인이 **기본 내부통제의 빈틈**이었다 — 금감원(6.24)은 배포 전 성능 검토·부하 시험·
  제3자 검증 누락, 금융위·금감원(10.14)은 24시간 관제 미구축·MFA 미도입. 그래서 변경관리·장애 판정·관제를 코드로 옮겼다. 산업은행 고유의 공개 지침은 찾지 못해
  산업은행에도 적용되는 전자금융감독규정·시행세칙, 공공기관 암호모듈(KCMVP), 한국은행이 감시하는 PFMI 를 기준으로 삼았다고 솔직히 적었다.
- Q. 변경관리는? → **배포 게이트** — `vm.sh update` 가 서비스를 멈추기 전에, 지금 배포된 코드가 새 설치본을 확인한다. 구문 오류·이미 적용된 마이그레이션 변경·
  정책 형식 오류는 어느 모드든 막고(서비스 중지 전), 바뀐 파일을 돈·인증·스키마 영역으로 묶어 위험도를 매기고, 그런 변경은 시험·부하 결과 없이는 승인이 안 된다.
  **요청자는 자기 변경을 승인할 수 없고**, 승인은 설치본 SHA-256 에 묶여 바꿔치기가 안 된다. 평일 08:30~16:00 은 배포 금지, 급하면 사유를 남기고 3일 안에
  다른 관리자가 사후 검토. 앱 계정은 변경 기록을 지우거나 해시를 고칠 수 없다(열 단위 권한).
- Q. 왜 지금 배포된 코드가 판정하나? → 새 설치본의 코드로 게이트를 돌리면, 새 코드가 게이트를 약하게 바꿀 수 있다. 이미 승인·검증된 쪽이 판정한다.
- Q. 1인 운영 VM 인데 승인이 막히면? → 기본은 '기록 모드' — 막지 않고 '미승인 배포'로 남기며, 수준진단 점검이 그것을 실패로 드러낸다. 금융 운영은 enforce.
  깨진 배포만은 어느 모드든 막는다 — 장애를 막는 게 목적이지 서류가 목적이 아니라서.
- Q. 장애는 어떻게 아나? → 1분마다 헬스를 부르는 합성 모니터링 — 10분 이어지면 장애 사건·경보, 30분이면(또는 10분 + 가입자 1만 명) 시행세칙 제7조의4 의
  **보고 대상**으로 표시하고 최초 보고 기한(인지 + 24시간)을 건다. 보고서 초안은 별지 제2호 12개 항목 순서 그대로이고, '사고원인(변경시점 및 사유 등)' 칸에
  **사건 전 24시간의 배포 기록**을 자동으로 붙인다 — 변경관리 기록이 곧 원인 추적의 출발점. 설정이 틀려 한 번도 정상 응답이 없던 주소는 장애로 보지 않는다(가짜 장애 방지).
- Q. 24시간 관제는? → 혼자서 24시간은 못 본다. 대신 **경보를 누가 언제 확인했는지** 남기고, 15분 동안 아무도 확인하지 않은 오류 경보는 한 번 더 보낸다(상향).
  확인까지 걸린 시간(MTTA)을 지표로 보고, 상위 관제(SIEM·금융권 통합관제)가 읽는 CEF·JSON Lines 로 내보낸다 — 아이디는 가명.
- Q. 취약점 점검은? → 금융보안원 침투테스트 가이드라인(2026.8)의 4단계(정보 수집 → 초기 침투 → 권한 상승 → 핵심 자산)로 22개 비파괴 점검을 만들었다.
  항목마다 ATT&CK 기법과 KISA 점검 항목 이름을 붙였고, 우리 주소가 아니면 승인 근거 없이는 시작하지 않는다. **처음 돌렸더니 실제 결함이 하나 나왔다** —
  예전 데모용 공용 실습 세션은 번호만 알면 누구나 읽고·진행하고·매매할 수 있었다(IDOR). 고치고 회귀 시험으로 묶었다. 수정 후 열린 경로 0.
- Q. 결과는? → 수준진단 3.21 → 3.26(시스템 설정 관리·보안사고 분석·관리가 고도화), CSF 2.0 근거 76 → 80/106, 모의훈련 7/7(장애 판정·깨진 배포 시나리오 추가 —
  깨진 설치본은 26ms 만에 서비스 중지 전 차단). 운영 점검은 20종.

## 4-4. DB 저장 표준·공간 효율·데이터 수명주기·DB 진단(ADR-0027, 2026-11)
**30초**: 운영 1년 규모(뉴스 100만 건 등)를 합성해 같은 데이터로 전/후를 쟀습니다. 날짜·시각을 문자열에서 date·timestamp 로, 원화 가격을 정수로
바꾸고, 180바이트 기사 주소 인덱스를 16바이트 md5 키로 바꾸고, 겹치는 인덱스 7개를 지워 **1,182MB → 807MB(−32%)** — 다시 만든 예전 구조와 견줘도
−26% 라 설계 효과입니다. 뉴스·검색은 13개월이 지나면 압축 보관(SHA-256 검증)한 뒤 정리해 3년 뒤에도 DB 가 약 0.69GB 에서 멈추고, 매일 크기를 기록해
디스크가 언제 찰지 예측·경보합니다.
- Q. 타입을 바꾸면 코드 전체를 고쳐야 하지 않나? → 저장만 바꾸고 값의 모양은 연결 경계에서 예전 그대로 맞췄다 — psycopg 연결마다 date·timestamp 를
  예전 문자열로 읽는 로더, 연결 시간대를 Asia/Seoul 로 고정. 서비스 수백 곳의 문자열 처리·화면 계약을 건드리지 않고, 깨지는 건 SQL 안의 문자열 연산
  (substr·LIKE·빈 문자열)뿐이라 그것만 고쳤다. 시험 41개가 처음에 깨졌고 원인은 전부 그 부류였다.
- Q. 시각은 전부 timestamptz 가 정석 아닌가? → 외부에서 받은 순간(시세·뉴스·메시지)은 timestamptz 로 했다. 업무 시각은 한국시간 벽시계 timestamp(0) —
  한국은 서머타임이 없어 모호하지 않고, 서비스가 받는 문자열 계약을 지킨다. 보안 표는 원래 timestamptz 였는데 연결 시간대를 고정하니 화면이 시각 앞부분을
  잘라 쓰던 곳의 9시간 어긋남도 같이 사라졌다.
- Q. 운영 DB 의 열 타입을 바꾸는 게 위험하지 않나? → 그래서 순서를 정했다. 표마다 ① 깨진 값을 세고(정규식 + 달의 마지막 날 — 2월 30일도 거름)
  ② 격리 표에 기본키와 원값을 남기고 ③ ALTER 한 번으로 표를 한 번만 다시 쓰고 ④ 바뀐 뒤 값 있는 행 수가 '전 − 깨진 값'과 같은지 대사해서 다르면 전체 롤백
  ⑤ ANALYZE. 1년 규모 실험에서 61~70초, 깨진 값 5개는 원값이 남았다. 되돌릴 수 없는 변경이라 이전 코드로 rollback 하려 하면 스크립트가 막고 백업 복원을 안내한다.
- Q. md5 는 깨진 해시 아닌가? → 보안용이 아니라 중복 판정 키다. 입력은 외부 RSS 주소라 의도적 충돌을 만들 동기가 없고 우연 충돌은 10^-26 수준. 조회도
  `md5(url)::uuid = md5(:u)::uuid AND url = :u` 로 원문까지 확인한다. 무결성(보관 파일)에는 SHA-256 을 쓴다.
- Q. 왜 파티션이 아니라 삭제인가? → PostgreSQL 유일 인덱스는 파티션 키를 포함해야 해서 기사 주소의 전역 유일성을 지킬 수 없다. 1년 100만 행이면 5,000건씩
  지우고 VACUUM 으로 빈자리를 재사용하는 게 맞다. 삭제 없이 시간순으로만 쌓이는 분석 계층 시세 이력은 이미 연도 파티션 + BRIN 이다.
- Q. 보관한 데이터는? → 달마다 gzip JSON Lines(뉴스 5.2배·검색 15배 압축), 쓰면서 SHA-256, 다시 읽어 검증한 뒤에만 DB 에서 지운다. 보관 기록은 앱 계정이
  지우거나 해시를 고칠 수 없고(V018), 복원은 해시부터 확인한다. 외부 보관 명령이 있으면 그 복사가 성공한 달만 지운다. 개인정보는 대상이 아니다 — 기한이 지나면 파기다.
- Q. 운영 감시는? → 매일 크기 1행 → 최근 60일 최소제곱으로 '며칠 뒤 디스크가 찬다'를 계산해 90일 안이면 경보. 죽은 행 비율·쓰이지 않는/겹치는 인덱스·캐시 적중률·
  XID 나이·연결·오래 열린 트랜잭션도 본다. 서버 설정은 메모리·CPU 로 계산(시험 가능한 파이썬)해서 update 때 바뀐 값만 ALTER SYSTEM, 재시작이 필요하면 한 번,
  안 뜨면 이전 설정으로 되돌린다. 백업은 zstd 로 바꿔 7.7배 빨라졌다.

## 5. 기업 신용위험 모형(ADR-0007)
**30초**: DART 다년 재무와 시장 피처로 '공시 후 1년 안 부실 징후' 확률을 추정했습니다. 공시일 기준(PIT) 표본, 사업연도 시간순 분할,
검증 연도로만 확률 보정, 그리고 Altman Z''·Merton 과 같은 시험 표본에서 비교했습니다.
- Q. 라벨은? → 관리종목·상장폐지 사유·정리매매·부도·회생·해산·채권은행 관리·영업정지 공시 + 다음 해 자본잠식 50% 이상. 실제 부도 데이터가 아닌 대리 변수라는 한계를 카드에 적었다.
- Q. look-ahead 를 어떻게 막았나? → 관측일 = 재무가 '공시된 날'. 결산일 기준이면 3개월 뒤에나 알 정보를 쓰게 된다. 시장 피처는 직전 월말, 사건은 관측일 이후만.
- Q. AUC 말고 왜 KS·PR-AUC·보정? → KS 는 신용평가 관행 지표, 부실이 드물어 PR-AUC 가 더 냉정, PD 를 충당금·한도에 쓰려면 '확률 자체'가 맞아야 한다(보정 그림).
- Q. 왜 로지스틱이 주 모형? → 심사는 '왜'를 설명해야 한다. 표준화 계수와 기업별 기여도로 '위험을 올린 요인'을 보여 줌. 부스팅은 비선형 비교용.
- Q. 결과는? → (합성) 로지스틱 AUC 0.830, Z'' 0.834 — 단일 요인 합성 데이터라 비슷한 게 정상. (실데이터) VM 결과를 그대로. 모형이 Z''를 못 이기면 그렇게 말한다.
- 꼬리: 공선성 → 자기자본비율(=1−부채비율)과 Merton DD 를 넣었더니 계수 부호가 뒤집혀 해석이 망가져 제외. 기대 방향과 반대 부호인 변수를 하나씩 빼는
  부호 검사를 넣었다 — 3개를 뺐고 AUC 는 0.829 → 0.830 그대로. "성능이 같다면 설명할 수 있는 모형"이 심사 모형의 기준.
- 꼬리: 왜 순위표를 안 만들었나 → 교육용 추정치가 실제 기업 평판에 낙인이 될 수 있어서. 정책금융 기관의 데이터 윤리와 연결.

## 6. 수익률 예측 검증(ADR-0008)
**30초**: '5일 뒤 오를 종목'을 맞히는 대신, 같은 모형을 무작위 K-겹과 시간순 전진+퍼지로 검증해 누수 크기를 숫자로 보였습니다.
예측할 것이 없는 합성 시장에서 무작위 분할은 IC t값 20, 비용 후에도 +61bp 라는 가짜 전략을 만들었고, 시간순은 AUC 0.498 로 정직했습니다.
- Q. 왜 누수가 생기나? → 5일 목표가 날마다 4일 겹친다(라벨 자기상관) + 이웃 날의 피처가 거의 같다 → 섞으면 학습·시험에 같은 문제가 들어간다.
- Q. 퍼지란? → 시험 구간 직전 5거래일 학습 표본은 목표 기간이 시험과 겹치므로 버린다. 학습은 항상 과거(확장 창)라 엠바고는 불필요.
- Q. 기준선은? → 무작위·20일 모멘텀·5일 반전. 신호를 심은 합성 시장에서 모형(0.577)이 모멘텀 한 줄(0.589)을 못 이겼다 → '기준선 못 넘음'.
- 꼬리: 은행 업무와의 연결 → 모형 검증(모형 위험 관리)의 기본: 표본 외 검증, 벤치마크, 결과가 나빠도 보고. 홈 추천 모형도 PSI(입력 분포 변화)·
  IC 추이·단순 모형 대비(Champion–Challenger)를 같이 공개한다.

## 7. 제로트러스트 — 신원·정책·데이터(ADR-0011~0014·0018)
**30초**: '내부망이니까 믿는다'를 없앴습니다. ① 접근 토큰 10분 + 1회용 갱신 토큰(재사용되면 탈취로 보고 세션 폐기)을 HttpOnly 쿠키로,
매 요청 세션·기기·유휴·계정 상태를 다시 확인 ② 모든 경로가 정책 엔진(코드와 분리된 JSON, 25개 동작)을 지나고 선언이 없으면 기본 거부
③ 앱 인가가 뚫려도 DB 가 한 번 더 막도록 개인 데이터 18개 표에 FORCE RLS ④ 민감 값은 값마다 키를 따로 쓰는 봉투 암호화.
- Q. 왜 JWT 가 아니라 서버 세션 조회? → 즉시 폐기(로그아웃·탈취 의심·관리자 강제 종료)가 핵심 요구. 비용은 로그인 화면 p95 약 +35ms(부하 시험) — 감수.
- Q. 쿠키로 바꾸면 CSRF 는? → SameSite=Strict + 세션별 CSRF 토큰(이중 제출) + Origin 검사. 출처는 포트까지 비교(같은 서버 다른 포트의 앱도 거부) —
  그 때문에 nginx 가 Host 의 포트를 떼던 설정에서 정상 로그인이 403 이 되는 결함을 실측으로 찾아 고쳤다(검증 보고서 결함 13).
- Q. 관리자는? → 상시 권한 없음. 자격(2인 승인으로 부여, 90일 재검토) + OTP 확인 세션 + 사유를 적고 30분만 활성(JIT). 개인정보 열람은 목적 필수 + 열람 기록(제8조).
- Q. RLS 의 한계? → 세션 변수는 앱 계정이 바꿀 수 있어 SQL 주입 공격자는 못 막는다 — 앱 로직 실수를 막는 2차 방어. 1차 방어(바인딩 100%·DDL 불가)와 함께.
- Q. 봉투 암호화의 이점? → 키 교체가 DEK 재포장만(본문 재암호화 없음). AAD 에 표·열·행 ID 를 묶어 암호문을 다른 행으로 옮겨 붙이면 복호화 실패.
- Q. XSS 는? → 화면 코드는 그대로 두고 실행 경로만 바꿨다 — 요청마다 새 nonce 의 CSP, Trusted Types, 인라인 이벤트 핸들러 0(`data-on` 허용 목록 해석기).
  위반은 `/csp-report` 로 보안 이벤트가 된다.
- Q. 스스로 만든 보안을 어떻게 검증했나? → 구현과 분리된 검토자 관점의 독립 점검을 따로 돌렸다. 유효 3건(로그인 직후 5분은 탈취된 세션도
  재인증 없이 고액 송금 가능 · RLS 쓰기 정책이 보낸 사람 위조를 못 막음 · compose 내부 컨테이너가 nginx 를 건너뛰어 헤더 위조)을 고쳤고,
  1건은 uvicorn 기본값을 실측해 오탐으로, 1건(남이 일부러 계정 잠그기)은 금융권 관행·규정을 근거로 감수로 판단했다 — '지적 = 수정'이 아니라 근거로 가른다.
- 꼬리: 성숙도 → KISA 제로트러스트 2.0 기준 자가 진단 21개 항목 중 이행 14·부분 6·미이행 1(단말 보안 상태 확인 — MDM/EDR 이 필요한 영역).
  '부분'은 대부분 외부 제품(KMS·SIEM·DLP 등)이 필요한 곳 — 예: KEK 가 아직 환경변수(KMS/HSM 이전이 다음 단계). 정직하게 '향상' 단계.

## 8. 가시성·자동 대응 — 감사 해시 체인·탐지 규칙
**30초**: 요청 ID 하나로 접근 로그·보안 이벤트·감사 기록을 잇고, 감사 로그는 해시 체인 + **매일 DB 밖에 남기는 외부 증인**으로
'관리자가 전체를 다시 계산해 덮어쓰는' 공격까지 잡습니다. 탐지 규칙 9개가 임계를 넘으면 IP 일시 차단·세션 폐기·알림을 자동으로 합니다.
- Q. 해시 체인은 전체 재계산하면 무력하지 않나? → 그래서 외부 증인(체인 머리를 날마다 파일·알림 채널에)과 대조한다(`run.py audit-verify`). 앱 계정엔 감사 로그 UPDATE/DELETE 권한 자체가 없다.
- Q. IP 는 개인정보인데 로그에? → 원문 대신 용도별 키 HMAC 가명값. 접속 기록에는 쿼리 값을 남기지 않는다.

## 9. 복원력 — 백업은 복원해서 검증된 것만(ADR-0019)
**30초**: RLS 도입 뒤 매일 백업이 조용히 실패하고 있었습니다(일반 계정 `pg_dump` 가 FORCE RLS 에 막힘). 백업 전용 계정·일관 스냅샷·age 공개키 암호화·

- Q. 가장 위험했던 실패는? → `--enable-row-security` 만 켜면 오류 없이 **빈 표**가 덤프된다(백업 '성공'인데 비어 있음). manifest 행 수 대조로 탐지, 시험으로 고정.
